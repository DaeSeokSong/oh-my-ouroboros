# 모델 배정 통합 규칙

> **로드 시점**: 작업 시작 전 subagent 모델 결정 시 (항상 적용)
> **전제**: 메인 세션 = 최상위 가용 모델 (머신별 pin은 README.md). subagent 모델은 별칭(opus/sonnet/haiku)으로 최신 자동 추적 — 특정 버전 하드코딩 금지. 메인 핀은 opus 별칭 이상이어야 §1 성립(상세: model-assignment-rules.md 머리).
> **핵심 원칙**: 메인 직접 처리 조건에 해당하지 않는 모든 작업은 반드시 적합 모델의 subagent에 위임한다. (planner·researcher는 opus 동급 subagent — "하위 모델"이 아니라 **분리 컨텍스트 위임**이 목적). **회색 지대(§1~§3 어디에도 안 걸리는 불확실한 작업)는 opus subagent 로 위임**한다(사용자 결정, 실측 근거: `rules-lazy/model-assignment-rules.md` §4).
> **second-opinion (opt-in)**: §1 고위험 결정(아키텍처·수식)은 사용자 명시 요청 시 Sonnet 독립 검토 1회 교차검증 — 상세: `rules-lazy/model-assignment-rules.md` §6

## 1. 메인 세션 직접 처리 조건

아래 중 하나라도 해당하면 메인 세션이 직접 처리한다. subagent 위임 금지:

| 조건 | 기준 |
|------|------|
| 수식·알고리즘 구현 | 수학 수식 포함 코드 |
| 도메인 타당성 검증 | domain-specific 메커니즘 판단 포함 |
| 아키텍처 설계·변경 | 모듈 간 인터페이스 변경 포함 |
| 복합 디버깅 | 인과관계 분석 + 로직 수정이 묶인 경우 |
| 사용자 합의 필요 | "검토"/"설계"/"타당성"/"비교" 키워드 포함 |
| 크로스 모듈 영향 | 수정 파일 ≥ 3개 + 모듈 간 의존성 변경 수반 |

→ 미해당 시: §2~§3 조건에 따라 subagent 위임

> **단일 Edit 예외 (`rules/prompt-routing.md` Step 1.5 위임 생략 조건과 정합)**: 단일 파일 + 단일 Edit 1회이고 해당 세션에서 연속 수정이 아니면 main 직접 처리를 허용한다. 2회째부터는 §2 Sonnet 위임 대상이다.

> **손과 결정의 분리**: 이 표는 **결정·검증·합의를 main 이 직접** 한다는 뜻이며, 코드의 **타이핑 자체**는 main이 설계 명세(수식·불변식·인터페이스·테스트 조건)를 쓴 뒤 coder에게 맡길 수 있다. 누가 타이핑하는지는 아래 «구현 갈래» 가 정하고, 타이핑에 한해 위 표의 «아키텍처 설계·변경» · «크로스 모듈 영향» 행보다 «구현 갈래» 가 우선한다(그 행들의 결정 · 합의는 그대로 main). (상세: `rules-lazy/model-assignment-rules.md` § 손과 결정의 분리).

> **소유권 (라우팅 1.9·5·6·9와의 관계)**: 자문·초안·지적 목록은 planner·researcher·reviewer에게, "검토·타당성·비교" 토론은 라우팅 9 teammate에게 위임할 수 있다. **최종 결정·사용자 합의는 main 소유**, 적용은 coder. 원문: `rules-lazy/model-assignment-rules.md` §8 소유권 각주.

### Whole-Job 예외 (과분해 견제)

**결합도 높은 다단계 작업**(단계 간 공유 컨텍스트가 크고 인수인계 비용이 모델 단가 차를 상회)은 단계별로 쪼개 위임하지 않고 **한 에이전트가 전체를 완주**한다 — main 직접 또는 적합 최고 모델 subagent 1개. 독립 병렬 작업엔 적용 금지, 위임 보고에 "whole-job: {결합 근거 1줄}" 명시. 판단 신호·남용 가드: `rules-lazy/model-assignment-rules.md` §7.

### 구현 갈래 (실측 근거: `rules-lazy/model-assignment-rules.md` §7.1)

| 구현의 종류 | 손 |
|---|---|
| 자기완결(함수 · 파일 하나, 다른 파일의 호출부가 바뀌지 않음) | main 명세 → coder(sonnet) |
| 결합도 높음(시그니처나 공개 동작이 바뀌어 정의 파일 밖의 호출부 · 시험을 함께 고쳐야 함) | 파일별 수정 명세를 따로 써서 넘기지 않는다. **opus 구현 subagent 1개**(`coder` 타입에 `model: opus`, 작업명 접두사 `opus:`)에 통째로 맡긴다. main 맥락이 이미 큰 경우도 같다 |
| 외부 검토 답 원문을 읽은 main 의 수정 | coder(읽기와 실행의 분리 그대로) |

- **판별**: 착수 전에 바꿀 함수 · 클래스의 호출부를 검색해(scout 또는 grep) 정의 파일 밖에서 함께 고쳐야 하는 파일이 하나라도 있으면 결합도 높음이다(이름은 그대로이고 인자 · 반환 · 동작만 바뀌는 경우도 같다). 없으면 자기완결이다.
- **넘기는 것**: spawn prompt 4요소에 과제 문장 · 제약 · 성공 기준(검증 명령)을 적는다. 수식 · 불변식 · 인터페이스 선택처럼 main 이 먼저 정해야 하는 결정(§1 표)은 «제약» 으로만 적고, 어느 파일의 어느 줄을 어떻게 고칠지는 적지 않는다.
- **검수**: 결합도 높은 구현이 끝나면 작성자와 다른 qa 와 reviewer(바뀐 함수 하나 지정)가 독립 검수한다. FAIL 은 같은 구현 subagent 로 반송하고 두 번 뒤에도 FAIL 이면 사용자에게 보고한다. main 이 직접 고친 결합 변경도 같은 검수를 받는다(직접 고쳐도 된다는 뜻이 아니다). 검수 착수 전 절차 원문: `rules-lazy/model-assignment-rules.md` §7.1 «검수 절차 원문».
- 검수 결과 채택은 main 소유이고, 단일 Edit 예외와 §3 의 5줄 이하 단서는 그대로다.

## 2. Sonnet subagent 위임 조건

아래 조건에 해당하면 Sonnet subagent에 위임한다:

| 카테고리 | 구체적 조건 |
|----------|-----------|
| **코드 구현** | 새 함수·클래스 작성 |
| **코드 수정** | 기존 함수 로직 변경 (단일 모듈 내) |
| **버그 수정** | 원인 파악 완료 후 단일 지점 수정 |
| **코드 분석** | 단순 탐색 이상의 구조 파악 |
| **모듈 추가** | 신규 파일 생성 (로직 설계는 메인 세션) |
| **설정 파일 수정** | rules/skills/agents .md 파일 내용 수정 |
| **문서 작성** | Confluence 초안 작성(조회·게시는 main), README 작성 |
| **Git 작업** | 커밋·브랜치·diff 분석 |

### Sonnet 위임 금지 조건 (메인 세션 직접 처리)
- 원인 분석이 아직 완료되지 않은 디버깅

## 3. Haiku subagent 위임 조건

**판단 기준**: 로직 판단, 사용자 승인, 도메인 특화 검증이 전혀 불필요한 작업

| 카테고리 | 구체적 조건 |
|----------|-----------|
| **코드 검증** | syntax/import 오류 확인, lint 결과 해석 |
| **파일 탐색** | 파일·함수·클래스 위치 검색 |
| **단순 수정** | 변수명·경로·주석 변경, 오타 수정 |
| **반복 수정** | 동일 패턴을 파일 3개 이상에 일괄 적용 |
| **소형 함수 수정** | 5줄 이하 단일 함수 수정 (수식·아키텍처 무관) |
| **테스트 실행** | 이미 작성된 테스트를 **실행만** 하고 PASS/FAIL 정리 (판정 로직 없음). ※검증 판단(6-Gate·인과 트레이싱·FAIL 원인 분석)이 걸리면 Haiku 아님 → qa(sonnet) 소관 — `agents/qa.md` |
| **로그 분석** | 에러 로그 파싱 및 수치 추출 |
| **포맷 변환** | 로직 없는 단순 포맷 변환 |
| **Dry-run 확인** | 실행 없이 출력만 확인 |
| **의존성 조회** | 패키지 버전·호환성 확인 |
| **설정 파일 탐색** | rules/skills/agents 파일 내용 읽기·검색 |
| **단순 문서 수정** | 오타·경로·날짜 등 로직 무관 문서 수정 |

### Haiku 위임 금지 조건 (Sonnet 이상 필요)
- 새로운 로직·알고리즘 설계 또는 구현
- 도메인 타당성 판단 포함
- 수식 구현 포함
- 디버깅 (단순 실행이 아닌 원인 분석 포함)
- 사용자와 합의가 필요한 설계 결정
- 기존 함수 동작 변경을 수반하는 수정 (예외: 아래 "5줄 이하 단일 함수 수정" 단서 충족 시)

> **우선순위 규칙**: Haiku 충분 조건과 금지 조건이 동시에 해당하면 **금지 조건 우선** — Sonnet 이상 사용 (단, "5줄 이하 단일 함수 수정" 단서는 이 규칙보다 우선하는 명시적 예외)

> **5줄 이하 단일 함수 수정**: 수식 구현 ❌, 아키텍처 변경 ❌, 사용자 합의 ❌, 동작 변경이 해당 함수 밖으로 전파 ❌ — 4개 모두 미해당 시 Haiku 위임 가능.
