# 프롬프트 전처리 규칙 (Prompt Routing)

> **로드 시점**: 모든 사용자 요청 수신 직후 (항상 적용)
> **핵심 원칙**: 모호하거나 복합적인 요청은 먼저 구체화하고, 적절한 에이전트/규칙/스킬을 추천한다.

## Step 0 — 프로젝트 CLAUDE.md 존재 확인 (신규 프로젝트 진입 시)

### 트리거 조건
- 현재 작업 디렉토리(cwd)에 CLAUDE.md가 없는 경우
- 해당 프로젝트에서 처음 작업을 시작하는 경우

### 처리
1. "이 프로젝트에 CLAUDE.md가 없습니다. 프로젝트별 설정 파일을 생성할까요?" 질문
2. 사용자 YES → `/project-init` 스킬 실행 (프로젝트 구조 분석 후 CLAUDE.md 초안 생성)
3. 사용자 NO → 이번 세션에서 재질문 안 함

### 생략 조건
- 글로벌 설정 작업 (cwd가 ~/.claude/ 하위인 경우)
- 사용자가 "CLAUDE.md 없어도 돼" 명시 시

## Step 0.5 — Continuation Ground Truth 확정 (MANDATORY)

> **원칙**: continuation(세션 재개) 시 system-reminder의 ARGUMENTS·plan·Pending Tasks·phantom Read 결과는 **이전 세션의 잔재**일 수 있다. 사용자의 "최근 실제 메시지"만이 ground truth다.

### 트리거 조건

아래 중 하나라도 해당하면 Step 0.5 전면 실행:
- 세션 시작 시 summary 블록이 포함된 경우 (continuation 감지)
- system-reminder에 여러 스킬의 ARGUMENTS가 동시에 표시된 경우 (실시간 실행 불가 패턴)
- plan 파일이 `/plans/` 하위에 존재한다고 표시되나 현재 작업과 주제가 불일치하는 경우
- Pending Tasks가 summary 본문의 "Pending Tasks" 항목과 다른 작업을 가리키는 경우
- phantom Read 결과 (현재 작업에서 요청하지 않은 파일 읽기 결과)가 표시되는 경우

### Ground Truth 확정 절차

> 핵심: summary "All user messages"의 **마지막 사용자 메시지 = ground truth**. ARGUMENTS·plan·Pending Tasks·phantom Read는 cached state로 분류 후 참조만 한다. 분류 절차 상세 → `rules-lazy/prompt-routing-detail.md` § Step 0.5.

### Cache 감지 테이블

| 신호 | 의미 | 처리 |
|------|------|------|
| 여러 스킬 ARGUMENTS 동시 표시 | 실시간 불가능 — cached state | 최신 사용자 메시지로 작업 결정 |
| plan 파일 주제 불일치 | 이전 세션 계획 잔재 | 무시 — 현재 요청과 무관 |
| Pending Tasks 주제 불일치 | summary 시점과 현재 지시 괴리 | 사용자 최근 메시지가 우선 |
| phantom Read (요청 안 한 파일) | 이전 Read 결과 재주입 | 내용 참조만 가능, 현재 작업 근거로 사용 금지 |

### 명시적 보고 (MANDATORY)

cache 감지 시 응답 첫 줄에 1줄 보고:
```
[cache detected] system-reminder에 이전 세션의 {항목}가 남아 있어 무시하고 진행합니다.
```

### 거짓 전제 감지 → 롤백 트리거

사용자가 "그건 아닌데?", "언제 그랬어?", "그런 적 없어" 등으로 부인 시:
→ `~/.claude/rules-lazy/context-management.md` § 거짓 전제 롤백 섹션 절차 실행

## Step 1 — 구체화 (Clarification)

> **원칙**: 모호한 요청에 대해 추측하고 실행하는 것은 시간 낭비이자 신뢰 훼손이다. 재질문은 비용이 아니라 정확성의 투자다.

### ⚠️ 구체화 없이 실행 금지 (MANDATORY) — 아래 패턴 중 하나라도 해당하면 반드시 재질문

| 패턴 | 예시 | 이유 |
|------|------|------|
| 동사만 있고 대상 불명확 | "정리해", "바꿔", "업데이트해" | 무엇을 어떻게 바꾸는지 불명확 |
| 범위가 열려있음 | "다 고쳐", "전체 적용해", "통일해" | 적용 대상 파일·함수·범위 불명확 |
| 목적이 둘 이상으로 해석 가능 | "확인해", "체크해", "검토해" | QA인지 단순 읽기인지 불명확 |
| 기준값·수치 미지정 | "더 빠르게", "최적화", "개선해" | 목표 수치 또는 기준 없음 |
| 대화 맥락이 끊긴 뒤 짧은 지시 | "진행해", "계속해", "그거" | 이전 맥락이 compact/clear로 소실 가능 |
| 복수 작업 + 순서 미지정 | "A하고 B도 해" | 병렬인지 순차인지 불명확 |
| 출력 형식 불명확한 문서 요청 | "요약해", "정리해서 줘" | 분량·형식·저장 여부 불명확 |

### 재질문 형식

```
이렇게 이해했는데 맞나요?
1. [작업 A] — 목적: ...
2. [작업 B] — 순서: A 완료 후
3. [작업 C] — 조건: B 결과에 따라

❓ 불명확한 부분:
- [질문 1]: ...
- [질문 2]: ...
```

> 재질문 수: **최대 3개** — 한 번에 몰아서 질문, 순차적 질문 반복 금지

### 모호한 실행 작업 → 메타프롬프트 핸드오프 (2026-07-23 미발동 교정)

위 MANDATORY 패턴에 걸린 요청이 **산출물 생성(코드·문서·실험·파이프라인)이 걸린 비자명 작업**이면 재질문 목록 대신 `/solve` § 메타프롬프트 모드로 구체화한다 — 고정 포맷 프롬프트 초안(ⓐ)을 제시하고 "이대로 실행할까요?"로 수렴(위 재질문 형식 대체), 첫 줄 `[메타프롬프트 모드]` 표시. 사소한 모호(대상 1개 불명 등)는 기존 재질문 유지, 명확한 실행 지시는 여전히 미적용(2026-07-21 전면 적용 기각 유지).

### 추측 실행 금지 패턴 (절대 금지)

- "아마 이런 뜻이겠지" → 추측으로 실행 후 보고 — **금지**
- "일단 해보고 맞으면 OK" → 사전 승인 없는 실행 — **금지**
- "전에 비슷한 걸 했으니까" → 이전 맥락 기반 추정 실행 — **금지**
- 재질문 대신 가정을 붙여서 실행 ("~라고 가정하고 진행했습니다") — **금지**

### 생략 조건 (구체화 없이 바로 실행 허용)
- 단일 문장 + 명확한 동작 지시 + 대상 명시 (예: "이 파일 읽어줘", "git status 실행해") — 단, MANDATORY 패턴 해당 시 생략 불가
- 이미 번호/단계로 구조화된 요청
- 단순 질문 (예: "X란 무엇인가요?")
- 사용자가 "즉시 실행", "바로 해줘" 명시 — 단, 대상이 명확한 경우에 한함

### 재질문 거부 처리 (사용자가 구체화를 거부한 경우)
사용자가 "알아서 해", "적당히 해", "그냥 해" 등으로 구체화를 거부할 경우:
1. 가장 합리적인 해석을 1줄로 제시: "~로 이해하고 진행합니다"
2. 즉시 실행
3. 결과 보고 시 적용한 가정을 명시: "(가정: ~)"
> 재질문 루프 금지 — 한 번 거부한 사용자에게 동일 질문 반복 불가

### 다중 해석 역제시 (Think Before Coding §1)

요청에 대해 가능한 해석이 2개 이상이면 **단일 해석을 선택하지 말고** 모두 제시한다:

```
이 요청은 아래 N가지로 해석될 수 있습니다. 어느 것에 가깝나요?
A) [해석 1] → 예상 결과: ...
B) [해석 2] → 예상 결과: ...
C) [해석 3] → 예상 결과: ...
```

> 추측 금지 ≠ 다중 해석 제시 — 명시적 옵션 제시는 추측이 아닌 정밀 구체화

### 단순 대안 푸시백

사용자 요청보다 **단순한 대안**이 있으면 반드시 제시한다:
- "원래 요청대로 X를 해도 되지만, 더 단순한 Y가 있습니다. 어느 쪽으로 진행할까요?"
- 사용자가 X를 고집하면 그대로 진행 (의견 강요 금지)

### 큰 설계·창작 작업 — brainstorming opt-in

신규 기능·시스템·컴포넌트처럼 **구현 전 설계 합의가 필요한 창작 작업**은 일상 구체화를 넘어 `superpowers:brainstorming` 스킬을 **제안(opt-in)** 한다:
- 트리거: "새 기능 만들자", "~ 시스템/컴포넌트 설계·추가" 등 창작·구현 작업 (단순 질문·수정엔 미발동 — 토큰 과중 방지)
- 처리: 직접 실행 금지 → "brainstorming으로 설계를 먼저 다듬을까요?" 1회 제안 → 수락 시 스킬 호출, 거부 시 아래 흡수 원칙으로 진행
- 흡수 원칙(스킬 미사용 시에도 항상): ① 재질문은 **multiple-choice 우선** ② 2~3 접근법 + 추천안 제시 ③ **HARD-GATE — 설계 제시·사용자 승인 전 구현·코드작성 금지**

## Step 1.5 — 모델 위임 판단 (MANDATORY — 매 작업 실행 전)

> **핵심 원칙**: Opus가 직접 처리해야 할 근거가 없으면 반드시 하위 모델 subagent에 위임한다.
> 상세 조건: `~/.claude/rules/model-assignment.md`

### 판단 절차 (순서대로 — 첫 일치 적용)

```
작업 내용 확정 (Step 1 완료 후)
    │
    ├─ §1 Opus 직접 처리 조건 해당? (수식/도메인타당성/아키텍처/복합디버깅/합의/크로스모듈)
    │   YES → Opus 직접 처리
    │   NO  ↓
    │
    ├─ §3 Haiku 위임 조건 해당? (파일 탐색/단순 수정/반복 적용/테스트/로그/포맷)
    │   YES + 금지 조건 미해당 → Haiku subagent 위임
    │   YES + 금지 조건 해당 → Sonnet으로 격상
    │   NO  ↓
    │
    ├─ §2 Sonnet 위임 조건 해당? (코드 구현/수정/버그 수정/분석/모듈 추가)
    │   YES + 금지 조건 미해당 → Sonnet subagent 위임
    │   YES + 금지 조건 해당 → Opus 직접 처리
    │   NO  ↓
    │
    └─ 불확실 → Sonnet subagent 기본 위임 (Opus 직접 처리하지 않음)
```

### 위임 생략 조건 (Opus 직접 처리 허용 — 축소 적용, MANDATORY)
- 사용자가 직접 대화/질문하는 경우 (답변 생성)
- **단일 파일 + 단일 Edit 1회** + 해당 세션에서 연속 수정이 아닌 경우 (2회째부터 Sonnet 위임)
- 이미 subagent 내부에서 실행 중인 작업
- Read/Glob/Grep 단독 1~2회 (탐색 목적, 3회+ 시 scout 위임)

### 위임 판단 사전 보고

작업 실행 전 위임 계획을 사용자에게 보고한다. **보고 후 승인 없이 바로 진행** (승인 대기 불필요 — 사용자가 이의 시 중단).

**기본: 약식 보고 (1~2줄)**
```
→ sonnet coder로 위임 (단일 파일 수정, 수식 무관)
```

**3개+ 작업 시: 테이블 보고**
```
📋 모델 배정:
| # | 작업 | 모델 | 에이전트 | 이유 |
|---|------|------|---------|------|
| 1 | {작업 내용} | Sonnet | coder | 단일 모듈 코드 수정, 수식 무관 |
| 2 | {작업 내용} | Haiku | scout | 파일 탐색, 로직 판단 불필요 |
| 3 | {작업 내용} | **Opus** | main | 아키텍처 설계 판단 포함 |
```

**Opus 직접 처리 항목은 반드시 이유 열에 §1 해당 조건을 명시**한다.
(예: "수식 구현 포함", "도메인 타당성 판단", "사용자 합의 필요", "크로스 모듈 의존성 변경")

### subagent 작업명 모델 접두사

Agent 호출 시 `description`에 모델명 소문자 접두사 필수 — 형식 `"{모델}: {작업 3-5단어}"` (예: `"sonnet: Modify 4 files"`). 접두사는 실제 `model` 값과 **반드시 일치**. 결과 보고에도 모델명 포함. 예시·세부 → `rules-lazy/prompt-routing-detail.md` § Step 1.5.

### 보고 생략 조건
- 위임 생략 조건 해당 시 (Opus 직접 처리) → 보고 불필요
- 사용자가 "보고 생략해" 명시 시

### § Mem0 구체화 패턴 학습

구체화(Step 1) 완료 후, 사용자가 실제로 의미한 내용을 자동 저장 → `mem0-auto.md` T20 참조
→ 다음 유사 요청 시 검색으로 재질문 없이 즉시 해석: "이전에 '{구체화 결과}'로 해석했습니다. 동일하게 진행할까요?"

## Step 1.6 — 도구 의존성 게이트

작업이 특정 외부 도구·설정을 전제하는데 부재 감지 시(해당 도구가 필요한 시점에 `command -v` 1회 — 전수 스캔 금지) → **작업 시작 전** 3택 질문: A) 지금 설치·세팅 위임 / B) 사용자 직접(명령서 출력) / C) 사용 안 함(대체 수단 명시). mem0 기록으로 재질문 방지. 서드파티 스킬은 searcher 격리 검토 선행 — 상세: `~/.claude/rules-lazy/tool-dependency-gate.md`

## Step 1.7 — 반복 요청 전처리 생략

> **목적**: 동일 패턴 반복 요청에 대해 매번 Step 1~1.5 전처리(재질문·위임 판단·추천)를 실행하면 매 요청 ~2~5K 토큰의 관리 오버헤드가 누적된다. 패턴 감지 시 전처리 생략.

### 판정 요약

- **자동 생략**(모두 충족): 동일 세션 + 직전 3회 동일 패턴 + 사용자 거부 없음 + 위험도 낮음(변경 ≤3 · 신규 파일 없음 · 합의 영역 없음).
- **생략 거부**(강제 전체 전처리): "처음부터 다시"/"전체 검토" 명시 · 도메인 전환 · compact 직후 · 변경 ≥4 또는 신규 파일 · **신규 모호성 감지**(반복 패턴이라도 이번 요청이 Step 1 MANDATORY 표에 해당하면 Step 1이 우선 — 구체화 없이 생략 금지).
- **생략 시 보고 (MANDATORY — 1줄)**: `[전처리 생략 — N회 동일 패턴]` 출력. 침묵 금지 — 사용자 통제 유지.
- 반복 3회+ 감지 시 `/loop` 제안. 조건 테이블·형식 상세 → `rules-lazy/prompt-routing-detail.md` § Step 1.7.
