## Step 1 상세 — 재질문 형식 · 다중 해석 역제시

> prompt-routing.md Step 1의 MANDATORY 표·생략 조건·거부 처리·단순 대안·brainstorming 문단은 always-on. 아래는 형식 상세.

**원칙**(2026-11-10 상시 Step 1 머리에서 이관): 모호한 요청에 대해 추측하고 실행하는 것은 시간 낭비이자 신뢰 훼손이다. 재질문은 비용이 아니라 정확성의 투자다.

**추측 실행 금지 패턴 예시**(같은 날 이관): "아마 이런 뜻이겠지" 추측 실행 · "일단 해보고 맞으면 OK" 무승인 실행 · "전에 했으니까" 이전 맥락 추정 실행 · 재질문 대신 가정 붙여 실행("~라고 가정하고 진행").

### 구체화 필수 패턴의 이유 (2026-10-02 상시 표에서 이관)

동사만 있고 대상 불명확=무엇을 어떻게 바꾸는지 불명확 / 범위가 열려있음=적용 대상 파일·함수·범위 불명확 / 목적이 둘 이상("확인해"·"체크해"·"검토해")=QA인지 단순 읽기인지 불명확 / 기준값·수치 미지정=목표 수치·기준 없음 / 맥락이 끊긴 뒤 짧은 지시=이전 맥락이 compact/clear로 소실 가능 / 복수 작업+순서 미지정=병렬인지 순차인지 불명확 / 출력 형식 불명확한 문서 요청("요약해"·"정리해서 줘")=분량·형식·저장 여부 불명확.

### 재질문 형식

```
이렇게 이해했는데 맞나요?
1. [작업 A] — 목적: ...
2. [작업 B] — 순서: A 완료 후 (작업 수만큼)

❓ 불명확한 부분:
- [질문 1]: ... (질문 수만큼)
```

> ❓ 불명확한 부분이 결과를 바꾸는 사용자 결정 항목(대상·범위·기준값 등)이면 번호 질문 대신 `answer-detail.md` § 문제·선택지 보고 형식의 선택지 표로 제시한다. 면제는 아래 「다중 해석 역제시 형식」과 같다(2026-09-15).

### 다중 해석 역제시 형식

```
이 요청은 아래 N가지로 해석될 수 있습니다. 어느 것에 가깝나요?
A) [해석 1] → 예상 결과: ...
B) [해석 2] → 예상 결과: ... (해석 수만큼)
```

> 해석 갈래가 결과를 바꾸는 사용자 결정 항목이면 위 A)/B) 목록 대신 `answer-detail.md` § 문제·선택지 보고 형식(선택지별 장단점·비교 표)으로 제시한다. 면제는 단순 사실 확인·기존 선택 확인·규칙 2 되묻기(결정 항목을 올린 뒤의 고도화 1~2문항)뿐이다(2026-09-15).

### 재질문 거부 처리 형식 (사용자가 "알아서 해" 등으로 구체화 거부 시)

1. 가장 합리적인 해석을 1줄로 제시: "~로 이해하고 진행합니다"
2. 즉시 실행. 단 **바꾸는 요청이면 이 1줄을 계획으로 올려 확정을 받은 뒤 실행한다**(CLAUDE.md 원칙 3, «알아서 해»·«적당히 해» 는 구체화 생략일 뿐 확정 면제가 아니다 — `rules-lazy/pre-work-summary.md` § 계획 확정). 바꾸지 않는 요청은 종전대로 바로 실행
3. 결과 보고 시 적용한 가정을 명시: "(가정: ~)"

### 재질문 수 상한 출처

재질문 수 최대 3개·판단 질문만 남기는 원칙은 grilling(MIT) 기법 이식 — 사실 확인은 에이전트가 조사하고, 사용자에게는 판단이 걸린 질문만 남긴다.

## Step 1.5 상세 — subagent 작업명 모델 접두사 (MANDATORY)

Agent 도구 호출 시 `description` 필드에 **모델명 소문자 접두사**를 반드시 포함한다.
하단 상태줄에서 어떤 모델이 작업 중인지 즉시 식별 가능하게 한다.

```
description: "sonnet: Modify 4 files"      ← Sonnet subagent
description: "haiku: Find related files"    ← Haiku subagent
description: "opus: Design architecture"    ← Opus subagent (researcher 등)
```

- 형식: `"{모델}: {작업 설명 3-5단어}"`
- **접두사는 실제 `model` 파라미터 값과 반드시 일치** — 불일치 시 거짓 표시 (예: description `haiku:` + model `sonnet` 금지)
- Opus subagent도 포함 (researcher 등 opus로 spawn하는 경우)
- 결과 보고 시에도 모델명 포함: `"sonnet: 수정 완료. 변경 파일 3개."`, `"haiku: 탐색 완료. 관련 함수 3건."`

## Step 1 상세: 큰 설계·창작 작업 brainstorming opt-in

> prompt-routing.md § 큰 설계·창작 작업의 정본 상세. always-on 에는 트리거 한 줄과 HARD-GATE 만 남겼다(2026-09-08 이관).

신규 기능·시스템·컴포넌트처럼 **구현 전 설계 합의가 필요한 창작 작업**은 일상 구체화를 넘어 `superpowers:brainstorming` 스킬을 **제안(opt-in)** 한다:
- 트리거: "새 기능 만들자", "~ 시스템/컴포넌트 설계·추가" 등 창작·구현 작업 (단순 질문·수정엔 미발동 — 토큰 과중 방지)
- 처리: 직접 실행 금지 → "brainstorming으로 설계를 먼저 다듬을까요?" 1회 제안 → 수락 시 스킬 호출, 거부 시 아래 흡수 원칙으로 진행
- 흡수 원칙(스킬 미사용 시에도 항상): 1) 결정 항목을 드러내고 **추천·유도 금지** — 각 항목에 한 줄 이력 + 한 줄 결론을 머리에 두고 선택지 2~4개·장단점·비교 표(정본: `answer-detail.md` § 문제·선택지 보고 형식)를 붙이고 답은 사용자가 만든다 2) 사용자가 결정·질문하면 **되묻기**로 선택지를 고도화하게 한다 3) **HARD-GATE — 설계 제시·사용자 승인 전 구현·코드작성 금지** (1번·2번: 2026-08-07 결정 주권, 2026-09-15 개정 — 상세: `rules-lazy/decision-sovereignty.md`)

## Step 1.7 상세 — 반복 요청 전처리 생략

> prompt-routing.md Step 1.7의 MANDATORY 1줄 보고와 신규 모호성 우선은 always-on. 아래는 판정 상세.
> **목적**: 동일 패턴 반복 요청에 대해 매번 Step 1~1.5 전처리(재질문·위임 판단·추천)를 실행하면 매 요청 약 2~5K 토큰의 관리 오버헤드가 누적된다. 패턴 감지 시 전처리를 생략한다.

### 자동 생략 조건 (모두 충족 시)

| 조건 | 기준 |
|------|------|
| 동일 세션 | 현재 conversation 내 |
| 직전 N회 동일 패턴 | 최근 3회 요청이 동일 동사·대상·범위 |
| 사용자 명시 거부 없음 | "다시 확인해" / "재질문해" 등 명시 없음 |
| 위험도 낮음 | 파일 변경 3개 이하, 신규 파일 없음, 사용자 합의 영역 없음 |

> 반복 패턴 3회+ 감지 시 `/loop` 스킬 제안 (비용 표 출력 후 사용자 결정). 상세: `rules-lazy/loop-auto.md`.

### 생략 형식

```
[전처리 생략 — N회 동일 패턴]
이전 요청과 동일하게 진행: {추정 작업 1줄}
→ 즉시 위임: {모델}/{에이전트}
```

### 생략 거부 — 강제 전체 전처리

- 사용자 명시: "처음부터 다시", "전체 검토", "다시 분석"
- 도메인 전환 감지 (코드 → 서칭 → 문서 등)
