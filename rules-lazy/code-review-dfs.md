# DFS 코드 리뷰 (한 함수씩 파고드는 리뷰)

> **로드 시점**: 브랜치·모듈 전체를 함수 단위로 훑는 리뷰를 시작할 때 lazy 로드.
> **정본 위치**: 이 파일이 방법론 정본이고, 실행 주체는 `agents/reviewer.md` 와 main 이다.
> **유래**: 2026-09-09~11 전수 리뷰에서 확립. 그 리뷰는 40개 수정 항목(C1~C40)과 여덟 건의 실측을 냈고, 아래 규율은 그 과정에서 실제로 사고를 막았거나 사고가 나서 생긴 것이다.

## 0. 이 리뷰는 무엇인가

**설계 의도와 코드의 어긋남**을 찾는 일이다. 동작이 맞는지 보는 qa(검증), 취약점을 보는 security 와 목적이 다르다.

| 묻는 것 | 예 |
|---|---|
| 이 값의 근거가 어디 있는가 | 문턱 1.6 은 어디서 왔는가 |
| 주석이 코드와 같은 말을 하는가 | 「1회 라운딩」이라 적혔는데 코드에 반올림이 없다 |
| 이름이 하는 일과 맞는가 | `area_px` 가 화소 수가 아니라 다각형 넓이다 |
| 이 갈래에 도달할 수 있는가 | `klg is None` 은 상류에서 절대 안 생긴다 |
| 설계 문서·논문과 같은가 | 페이지는 `max`, 코드는 `min` |

## 1. 진행 규칙 (MANDATORY)

1. **한 번에 한 함수.** 진입점에서 시작해 호출 순서대로 내려간다.
2. **파고들기 전에 사용자 허락을 받는다.** 「다음은 X 입니다」까지만 말하고 멈춘다. 허락 없이 내려가면 그 분량이 통째로 버려진다(실사고 2026-09-09).
3. **사용자가 질문 중이면 답변만 한다.** 질문이 안 끝났는데 다음 함수로 가지 않는다.
4. **코드를 그 자리에서 고치지 않는다.** 전부 변경 문서에 모아 **일괄 적용**한다. 리뷰 도중의 수정은 뒤 항목의 전제를 흔든다.

## 2. 한 함수를 내놓는 형식

```
경로: 진입점 → ... → 여기            (breadcrumb)

무엇을 : 한 줄
어떻게 : 한 줄
왜     : 한 줄

| 단계 | 줄 | 무엇을 | 어떻게 | 왜 |     (표)

## 짚은 것                              (번호 목록, 값에 영향 주는 것에 ★)
```

## 3. 짚을 때의 규율 (MANDATORY)

- **근거 없는 값은 「임의로 정한 값」이라 쓴다.** 「적절한 값」·「최적값」으로 포장하지 않는다. 육안 판정이면 육안 판정이라 적는다.
- **주장 전에 잰다.** 캐시된 자료로 실측하고, 산술 주장은 작은 스크립트로 검증한 뒤 그 출력을 근거로 쓴다. 「~일 것이다」로 지적하지 않는다.
- **★제안한 수정이 출력을 바꾸는지 반드시 판정해 적는다.** 바꾸지 않는 항목과 바꾸는 항목을 갈라 두면 일괄 적용 때 기계 대조가 가능해진다.
- **소비자를 확인한다.** 그 키를 다른 저장소가 읽는지 grep 으로 본다. 안 읽으면 걱정거리가 아니다.
- **설계 원본과 대조한다.** 논문·컨플루언스 결과 보고·이전 커밋. 원문이 유료면 사용자에게 사본이 있는지 묻는다.
- **보이지 않는 계약도 본다.** 자료형(`float` 대 `int`) · 줄바꿈(CRLF 대 LF) · 직렬화 경로 · 좌표 순서 · 배열 dtype.

## 4. 결정은 사용자 몫

갈래를 **같은 형식으로** 나열하고 각 갈래에 **한 줄 이력 + 한 줄 결론**만 붙인다. 추천 표시·`(권장)`·굵게 강조로 답을 흘리지 않는다(`rules-lazy/decision-sovereignty.md` 와 같은 규율).

```
| 갈래 | 한 줄 이력 | 한 줄 결론 |
```

## 5. ★적용 전 합동 점검 (MANDATORY)

항목을 하나씩 볼 때 안 보이던 것이 **함께 적용하면** 드러난다. 적용본을 실제로 만들어 아래를 본다. 이 단계를 건너뛰면 네 건짜리 논리 오류가 그대로 들어간다(실사고 2026-09-11, get_osp.py).

| 점검 | 실제로 나온 예 |
|---|---|
| 두 항목이 같은 줄을 만지는가 | 「복사본 반환」과 「팽창 제거」가 같은 줄에서 병합됐다 |
| 한 항목이 다른 항목의 전제를 무너뜨리는가 | 면적을 외곽선에서 떼자 「외곽선 없으면 조기 반환」이 면적까지 막았다 |
| 자료형이 바뀌는가 | `int(countNonZero(...))` 가 실수를 정수로 바꿨다 |
| 예외 처리 안에 새 실패 지점을 넣지 않는가 | `except` 안의 로거 임포트가 디렉터리를 만들다 실패해 부분 결과 반환을 깨뜨렸다 |
| 성능이 뒤집히는가 | 싼 검사를 지우고 비싼 검사를 남겨 라벨링이 9.7%에서 100%로 늘 뻔했다 |
| 미사용 변수가 남는가 | 다시 쓰면서 `h` 가 계속 안 쓰였다 |

## 6. 기록 형식

변경 문서 **한 개**에 모은다. 위치는 `docs/handover/<브랜치>-code-review-changes.md`.

```
| # | 파일 | 위치 | 상태 |      ← 적용 대상 표 (맨 위)
## C<n>. 한 줄 제목
### 무엇을 / ### 어떻게 / ### 왜
| 갈래 | 한 줄 이력 | 한 줄 결론 |   ← 결정이 필요한 것
## 검토했으나 수정하지 않기로 한 것    ← N 항목
## 실측 근거                          ← 스크립트와 결과
```

- **번복은 지우지 말고 「정정」으로 남긴다.** 왜 뒤집혔는지가 다음 사람에게 값어치가 있다.
- 다만 결론이 확정되면 **최종안 블록**을 만들어 「이 블록이 정본이다」라고 표시한다. 경위와 정본을 섞어 두면 읽는 사람이 무엇이 살아 있는지 모른다.
- 게시·기록 전 `python3 ~/.claude/scripts/korean_style_check.py <파일>` 차단 0건.

## 7. 흔한 함정 (전부 실측으로 확인된 것)

| 함정 | 사실 |
|---|---|
| `cv2.contourArea` 를 화소 수로 읽음 | 경계 화소 **중심**을 잇는 다각형이라 `n×n` 이 `(n−1)²`. 작을수록 손해가 크고 1화소 두께는 0 이 된다 |
| z-score 로 「떨어진 거리」를 잼 | 분자와 분모가 둘 다 거리에 비례해 **거리가 약분된다.** 상한은 `sqrt(상대 개수 / 자기 개수)` 라 사실상 개수 비 검사다 |
| `2*(w//3)` | `(2*w)//3` 와 다르다. 정수 나눗셈을 두 번 쓰면 중심이 밀린다 |
| numpy 실수 판정 | `np.float64` 는 `float` 의 서브클래스지만 `np.float32` 는 아니다 |
| 부호 있는 문턱 검사 | `z > ths` 는 한쪽만 거른다. 절댓값이 필요한지 본다 |
| 같은 이름 함수 두 번 정의 | 파이썬은 **뒤엣것**만 남긴다. 앞엣것을 고쳐도 아무 일도 안 일어난다 |
| 팽창 뒤 지우기 | `dilate` 한 영역을 0 으로 만들면 **이웃 덩어리도 깎인다** |
| 연결 요소 이어짐 | `scipy.ndimage.label` 기본은 4방향. 8방향으로 바꾸면 대각 한 화소가 다리가 되어 덩어리가 통째로 묶인다 |
| 좌표를 되돌리는 층 | letterbox 되돌리기와 여백 빼기가 **두 겹**이다. 한 겹만 되돌리면 조용히 어긋난다 |

## 8. 실측이 필요한 신호

아래가 보이면 재고 나서 말한다.

- 「이 단계가 실제로 결과를 바꾸는가」: 단계별로 켜고 꺼서 최종 산출물이 같은지 센다
- 「이 문턱을 옮기면 몇 건이 달라지는가」: 문턱 후보별 건수와 변화량 분포
- 「이 잣대를 바꾸면 순위가 바뀌는가」: 잣대별 상위 N 불일치 건수
- 「이 갈래에 실제로 들어오는가」: 도달 건수부터 센다. 0 이면 지적의 무게가 달라진다

측정 스크립트는 `<프로젝트>/.scratch/<세션 id>/` 에 파일로 쓰고, 머리말에 **왜 재나 · 무엇을 재나 · 무엇을 뜻하나**를 적는다.
