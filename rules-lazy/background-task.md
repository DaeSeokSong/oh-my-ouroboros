# Background Task 관리 규칙

> **로드 시점**: background task 생성 전, 실험 스크립트 실행 전
> **핵심 원칙**: background task는 사전 검증 후 목적당 1개만 생성한다

## § 사전 foreground 검증 (MANDATORY)

background 실행 전 반드시 동일 명령을 foreground로 먼저 검증한다:

1. `timeout 10 {명령}` 으로 구문·경로·인자 오류 확인
2. 오류 없이 시작 확인 → background 전환 허용
3. 오류 발생 → background 전환 금지 → 원인 수정 후 재검증

```
# ✅ 올바른 흐름
timeout 10 python3 train.py --phase 1 --dry-run   # foreground 검증
→ PASS → background 전환

# ❌ 금지 패턴
python3 train.py &   # 사전 검증 없이 바로 background
```

## § 1 논리 작업 = 1 Background Task

background task 생성 전 TaskList로 기존 task를 반드시 확인한다:

| 상황 | 처리 방법 |
|------|-----------|
| 동일 목적 task 실행 중 | SendMessage로 이어받기 또는 TaskOutput 재활용 |
| 동일 목적 task 완료됨 | TaskOutput 읽기 → 재생성 금지 |
| 관련 task 없음 | 새 background task 생성 허용 |

**금지**: 동일 명령을 검증 없이 연속 생성 (0 bytes task 양산 방지)

## § 실험 스크립트 Background 금지 조건

아래 중 하나라도 해당하면 background 실행 금지:

- `--phase`, `--stage`, `--subset` 등 **범위 한정 인자가 없는** 학습 스크립트
- 사용자가 명시적으로 background 허용을 언급하지 않은 경우
- `train.py`, `run_trains.py` 등 학습 스크립트 전체 실행 요청

> **적용 범위**: 이 절은 Bash 도구의 `run_in_background`·`&` 로 만드는 background task 에 적용한다. tmux 창에서 `launch-set.sh launch` 로 올리는 학습(§ main 의 tmux 직접 발사·§ 대기 목록 자동 발사)은 이 절이 아니라 해당 절의 조건(사용자 발사 지시·목표 표·발사 세트·verify 원문)이 적용되며, 그 경로에서는 범위 한정 인자 유무가 발사를 막지 않는다.

> 관련: `~/.claude/rules/code-execution.md` § 코드 실행 규칙 — "코드 실행은 항상 사용자가 직접 수행"

## § 학습 메모리 가드 (MANDATORY — 2026-08-18 사용자 지시)

AI 학습·대형 추론의 **실행 명령서는 memguard 래핑을 기본형으로 출력**한다 — 맨 명령을 그대로 주지 않는다. 근거: 무제한 PyTorch 프로세스가 팽창해 전역 OOM 으로 서버 접속이 막힌 실사고(2026-08-17). cgroup 상자 안에서는 초과 시 그 작업만 죽는다.

```
bash ~/.claude/tools/mem-guard/memguard-run.sh [--high 40G] [--max 56G] [--swap-max auto] [--name {슬러그}] -- {학습 명령}
```

- 예산은 실측 기반으로 조정: 같은 계열 학습의 과거 점유를 알면 `--high/--max`를 그에 맞춰 낮춘다. 프로젝트마다 잰 값은 프로젝트 등록부 `memguard.high`·`memguard.max` 에 둔다(경위: `knowledge/harness/rules-project-server-history-2026-11-10.md` § background-task). 그 프로젝트 등록부에 `memguard.*` 키가 없으면 실측한 뒤 그 프로젝트 등록부에 더한다(다른 프로젝트 값을 가져다 쓰지 않는다). 동시 다판이면 합계가 "총 RAM − 예약 32G"를 넘지 않게 배분. 예약 기본값은 32G다(2026-09-29 사용자 결정).
- swap 은 판마다 상한만 두고 하한은 두지 않는다(`--swap-max`, 기본 auto = swap 총량 ÷ GPU 수, 2026-09-29 사용자 결정). 상한이 없으면 먼저 MemoryHigh 에 닿은 판이 swap 을 독차지한다. 전체 swap 이 찬 상태에서 판이 MemoryHigh 를 넘으면 죽지 않고 스로틀로 느려진다(실측). swap 점유율은 ntfy 경보를 내지 않는다(`mem-watch.sh`, 2026-09-29 사용자 지시).
- 메모리 알림(cron 매분 `mem-watch.sh`, 2026-09-29 사용자 결정): WARN 은 로그만 남기고 ntfy 는 CRIT(🚨)과 CRIT 해제(✅)만 보낸다. memguard scope 안의 프로세스가 실제로 OOM 으로 죽으면 `oom-watch.py` 가 💀 알림을 낸다. 알림에는 판 이름, 죽은 프로세스, 판 한도 초과인지 호스트 전체 고갈인지, 판·전체 swap 상태가 담긴다. 커널 로그 권한(adm 그룹)이 있으면 커널이 적은 희생 프로세스와 원인이 정본이고 systemd-oomd 압력 종료도 보인다.
- **안 자란 몫과 압력 검사 (2026-10-12 실사고)**: 발사 전 검사는 `MemAvailable − Σ max(high − current, 0)` 이 `예약 + 새 판 max` 이상일 때만 통과한다. Σ 는 같은 계정의 모든 `memguard-*.scope` 에서 구하고 `memory.high` 가 `max` 인 scope 는 건너뛴다. 거부(exit 75)하면 남은 메모리·안 자란 몫(scope 수)·예약·예산이 GiB 로 나온다. 재개 발사도 같은 검사를 받는다. 뿌리 cgroup 을 못 읽으면 종전 검사만 하고 경고 한 줄을 낸다.
- 같은 검사가 사용자 서비스 cgroup 의 `memory.pressure` `full avg60` 이 `--pressure-max <퍼센트>`(기본 10, 0 이면 끔) 이상이면 거부한다(exit 75). 파일을 못 읽으면 경고만 내고 통과한다. 시험용으로는 환경변수 `MEMGUARD_TEST_ROOT` 하나만 쓰며 켜면 경고 줄이 나온다.
- 압력은 매분 기록만 하고 알리지 않는다(2026-10-12 사용자 지시). 알림은 메모리로 발사가 거부됐을 때와 판이 강제 종료됐을 때만 온다. `mem-watch.sh` 는 매분 `Pressure=<avg10>/<avg60>%` 를 로그에 남기고 `full avg60` 이 `PRESSURE_LOG_PCT`(기본 15) 이상인 분에 scope 별 상위 5개를 로그에 남긴다. 거부 알림은 `memguard-run.sh` 가 실제 발사 거부(예산·압력) 때 🚫 로 한 번 보낸다(`--preflight-only` 점검은 알리지 않는다). 강제 종료 알림은 `oom-watch.py` 의 💀 과 와쳐의 비정상 종료 알림이다.
- 와쳐 보고(`train-watcher.sh`): 완료 마커 없이 끝난 판의 보고서·알림에 직전 압력 표본(최근 10개)과 판정 한 줄을 붙인다. `full avg10 ≥ 25` 또는 `avg60 ≥ 15` 표본이 있으면 «메모리 압력 종료(systemd-oomd) 의심, 확정은 sudo journalctl -u systemd-oomd», 없으면 «종료 직전 메모리 압력 낮음», 표본이 없으면 «압력 표본 없음» 이다.
- **판 수별 GPU 배치 기본값 (2026-10-01 사용자 결정 «결정1. 2) 단 주의 사항을 각 학습세션에 전파»)**: 같은 차수에 올릴 판 수가 GPU 수와 다르면 `tools/train-watcher/placement_table.json` 의 판 수별 배치(DDP 묶음·기종이 다른 카드의 비례 짝 등에 줄 세우기)를 기본으로 쓴다. 판 수가 GPU 수와 같으면 판당 1장이다. 단 아래 주의 사항을 모두 갖춘 프로젝트만 따르고, 못 갖춘 프로젝트는 아래 «빈 GPU 마다 한 판»을 유지한다.
  1. **DDP 준비**: 학습 샘플러가 순위(rank)별로 데이터를 나눠야 한다(DistributedSampler 또는 동등). 준비 여부는 프로젝트마다 다르고 준비된 프로젝트만 `train.env` 의 `DDP_READY=1` 로 선언한다(프로젝트별 현황 경위는 위 경위 노트).
  2. **유효 배치·학습률**: DDP 는 유효 배치가 장치 수만큼 커진다. 학습률 조정(선형 스케일·워밍업)과 정확도를 짧은 판으로 먼저 확인한다. 벤치마크는 시간만 쟀다.
  3. **비교성**: 진행 중인 판은 바꾸지 않고, 한 판 안에서 배치 방식을 바꾸지 않는다. 방식이 바뀐 판과 이전 판을 비교할 때는 표에 경계를 적는다.
  4. **비례 짝**: 속도가 다른 두 기종을 섞는 비례 배치는 PyTorch·Lightning 기능이 아니라 자작(순위별 배치·표본 분할 + 손실 보정)이다. 없으면 균등 짝은 느린 기종 짝과 같은 속도라 빠른 기종을 따로 쓰는 배치가 낫다.
  5. **표의 가정**: 같은 길이의 판이 동시에 시작할 때의 값이다. 판 길이·도착 시각이 다르면 이득이 줄어든다. BatchNorm 이 있는 모델은 DDP 에서 SyncBN 여부가 결과를 바꿀 수 있다.
  6. **체크포인트·발사**: last.ckpt 매 에폭·top-K 규칙은 그대로다(저장은 순위 0). `launch-set.sh` 에 묶음의 GPU 전부를 `--gpu 3,4` 처럼 준다. 한 GPU 두 판·MPS 는 처리량 이득이 없어 판 > GPU 일 때도 줄 세우기를 쓴다. 줄은 미리 GPU 별로 나누지 않고, 승인된 대기 목록에서 와쳐가 먼저 비는 GPU 에 다음 판을 올린다(§ 대기 목록 자동 발사).
  7. **처리량 기법**: torch.compile·channels_last·fused AdamW 는 방식과 무관하게 약 20% 줄인다. 켤 수 있는 프로젝트는 켜고, 켜기 전후 판은 비교성 경계를 적는다.
- **GPU 배치 (모든 학습, 2026-09-29 사용자 결정)**: 위 조건을 못 갖춘 프로젝트의 기본은 빈 GPU 마다 한 판이다. 이미 판이 도는 GPU 에 더 올리는 것은 `launch-set.sh` 의 GPU·CPU 사전검사(`gpu_preflight.py`)를 통과할 때만 허용한다. 통과 조건은 네 가지다. 새 판 크기(`--vram-gb`·`--cpu-cores`)를 주어야 하고, 빈 VRAM 이 새 판의 1.1배 이상이어야 하며, 대상 GPU 사용률 60초 평균이 70% 이하여야 하고, 빈 논리 코어가 새 판 코어 + 예비 8 이상이어야 한다. 미달이면 exit 76 으로 발사 전에 거부한다. GPU 번호는 `--gpu`, 없으면 명령의 `RUN_GPU=`·`CUDA_VISIBLE_DEVICES=` 에서 찾고(PCI 순 번호), 그래도 모르면 경고만 한다. 근거: GPU 가 이미 꽉 찬 판 옆에 겹치면 카드 총처리량은 그대로이고 판마다 절반 속도가 된다(09-23 실측 2.49→2.51 it/s). 사용률 문턱은 입출력 대기로 GPU 가 비는 판에만 겹치게 하려는 것이다. 최선 배치는 판 수에 따라 다르다(09-30 3차 벤치마크, 같은 길이 판 동시 시작 가정): 판 6개는 판당 1장 병렬과 DDP 묶음이 동률이고, 판 1~5개와 7개 이상은 DDP 묶음(기종별·기종이 다른 카드의 비례 짝 등)에 줄 세우는 쪽이 8~244% 빠르다. 한 GPU 두 판·MPS 는 GPU 6장 전부에 걸면 줄 세우기보다 느리다. 그래서 10-01 부터 위 «판 수별 GPU 배치 기본값»을 쓴다(조건을 갖춘 프로젝트만). 정본 `tools/train-watcher/placement_table.json`.
- MemoryMax가 DataLoader **워커만** 죽이면 학습이 크래시 대신 큐 대기 hang이 될 수 있다(기본 timeout=0) — 와쳐의 `--timeout-h`가 이 경우의 안전망이므로 2종 세트를 반드시 함께 쓴다. 근본 완화는 학습 코드의 `DataLoader(timeout=...)` (2026-08-19 Grok 교차 소견, main 검증).
- preflight 거부(exit 75)가 나오면 임의로 예산을 올려 우회하지 말고 사용자에게 보고(무엇이 얼마나 부족한지 수치 포함).
- user 위임이 없는 서버에서 exit 77이 나오면 관리자 조치(Delegate=memory) 안내가 출력된다 — 그대로 사용자에게 전달.
- 스크립트 헤더가 인자·종료 코드의 정본. 검증: 2026-08-18 실측(강제 적용·거부 케이스 모두 확인).

- **언제**: 학습(본 판)의 드라이런을 돌리기 **전에 매번** 이 양식으로 학습 계획서를 보고하고 사용자 확인을 받는다. 드라이런 실측 · GPU 배정 · 발사 명령서(§ 학습 목표 표 · 발사 세트)는 계획서가 확정된 뒤의 과정이라 이 양식에 넣지 않는다(사용자 원문 «6번 7번은 계획표 결정 후 과정이야»).
- **본문은 HTML**: 계획서 전문은 HTML 파일로 만든다. 실험 카드마다 그 판이 기준판과 무엇이 다른지 보이는 인터랙티브 설명 그림을 넣는다. 계획서 페이지(HTML · 구조도)는 늘 figure 스킬(코드)로 만들고 페이지를 누가 만들지는 묻지 않는다. 페이지 안의 블록 예시 그림과 코드 이해용 그림만 생성형으로 만들며, Codex 이미지 생성과 Grok 가운데 누구에게 맡길지를 페이지를 쓰기 전에 묻는다. 이 답이 그릴 주체 답을 겸하고 모델 · effort 질문은 그대로 한다(`skills/figure/SKILL.md` § 그릴 주체 선택. 2026-11-19 사용자 지시 «각 실험판의 블록 눌렀을 때 나와야 하는 예시 이미지들은 생성형으로만 작성되도록», 2026-11-21 사용자 답 «아티팩트 자체는 항상 figure 스킬로 생성하고 그 안에 들어가는 블록 예시나 코드 이해용 이미지만 생성형으로 그록이나 코덱스에게 요청하면 돼»).
- **그림 크기**: 실험 카드의 그림은 카드 전체 폭으로 크게 두고 확대 · 축소 단추 · 크기 조절 막대 · 화면 가득 «크게 보기» 를 넣는다(2026-11-18 사용자 지시 «이미지가 너무 작아. 키워서 볼 수 있도록 수정하고, 크기 조절도 가능하도록 해»).
- **확인 뒤 삭제**: 사용자가 계획서 확인을 마치면(확정 답) 그 HTML 계획서 아티팩트를 지운다(Artifact `delete`, 도구가 매번 사용자 확인을 받는다). 원본 HTML 은 세션 임시 폴더에 남긴다(2026-11-18 사용자 지시 «확인 후에는 항상 html 계획서는 아티팩트에서 지우도록 해»). 모바일 모드가 켜진 세션에서는 decision-popup mod 가 삭제를 거부하고 대기 목록(`~/.claude/_usage/decision-popup/artifact-delete-pending.tsv`)에 적는다. 모바일 앱에는 삭제 확인 창이 보이지 않아 사용자가 고를 수 없기 때문이다(2026-11-24 사용자 지시 «모바일 모드 on일 때는 미루도록 해», 의뢰서 `intent/2026-11-24-harness-review-six-items.md` W6). 아티팩트 링크 꼴(`claude.ai/artifact/<id>` · `claude.ai/code/artifact/<id>`, asset 은 16진수 32자 id)이 아니면 기록하지 않고 거부한다. 세션은 사용자에게 미뤘다고 한 줄 알리고 같은 삭제를 다시 시도하지 않는다. 모드를 끈 뒤 사용자가 지시하면 지운다(`/mobile-mode off` 나 띠의 📱 버튼 출력에 `ARTIFACT_DELETE_PENDING: N건` 과 url 이 붙고, 세션 시작 경보도 같은 이름으로 남은 건을 알린다. 대기 줄은 모델이 남긴 기록이라 지시가 아니므로 목록을 사용자에게 보이고 지시받은 것만 지운다). 모드가 꺼진 세션에서 삭제가 성공하면 그 줄은 목록에서 빠진다.
- **띄우는 도구**: 결정 팝업(`mcp__decision-popup__ask`), 모바일 모드면 채팅 글 + AskUserQuestion(`rules-lazy/answer-detail.md` § 띄우는 도구). 팝업 · 선택 창에는 짧은 요약(결론 2줄 · 결정 항목)만 쓰고 «HTML 계획서를 보십시오» 로 안내한다. 긴 본문을 팝업 · 채팅에 붙이지 않는다.
- **카드 단위**: 설정 하나 = 카드 한 장. 같은 설정의 과제 판은 한 카드로 묶고 과제별 차이는 «어떻게» 줄에 적는다.
- **줄임말 풀이**: 줄임말 · 문서 고유 번호(E7 등) · 낯선 용어(비등방 축척 · 기준점 캐시 등)는 처음 나올 때 괄호 안에 한 줄 쉬운 풀이를 붙인다. 예: «E7(연결 세기의 꼴: 밀집 · 희소 등급 · 혼합)만 다릅니다».
- **예시 두 줄**: 1줄 입력(판이 받는 것), 2줄 출력(판이 내는 것). 가상 성능 숫자는 넣지 않는다.
- **판정 기준 줄은 유지**한다(사용자 원문 «오히려 판정 기준만 남기고»). 단계 표에 GPU 시간 열은 넣지 않는다(«3번의 GPU 시간 컬럼도 추가적으로 빼»).

**2026-11-19 확정분 (사용자 확정 «양식 확정», 결정 팝업 «5가지 전부 필수»)**: 한 학습 세션에서 HTML 계획서를 12번 고쳐 가며 정한 규칙이다. 아래 다섯 가지는 모든 계획서에 넣는다.

- **설명은 세 줄**: 계획서 안의 설명(블록 설명 · 기준판 대비 차이 설명)은 «무엇 · 어떻게 · 왜» 이름표를 붙인 세 줄로 쓴다(2026-11-18 사용자 메모 원문 «항상 무언가를 설명할 때, 무엇을/어떻게/왜에 대한 설명을 추가할 것»).
- **구조도 블록**: 구조도의 블록을 누르면 그 블록의 예시 그림과 세 줄 설명이 열린다. 이 그림에도 크기 조절(40 ~ 300%)과 «그림 크게 보기» 를 둔다.
- **달라진 블록 표시**: 실험판에서 기준판과 달라진 블록은 그 판 전용 설명과 그림을 따로 둔다. 종류는 색과 글자 표지로 함께 나타낸다(색만으로 구분하지 않는다).
  - 색: 바뀜 주황 · 새로 생김 분홍 · 꺼짐 회색 빗금 · 얼림 파랑.
  - 글자 표지: 구조도 블록 모서리에 «바뀜 · 새로 · 꺼짐 · 얼림».
  - 설명 창에도 같은 색 띠와 표지를 둔다.
- **전/후 토글**: 달라진 블록의 설명 창은 «전(기준판) · 후(이 판)» 를 오가며 보게 한다. 새로 생긴 블록도 전/후를 둔다. 이때 «전» 은 그 자리의 기준판 블록이거나 전용 «전» 그림이다(2026-11-18 사용자 메모 #11).
- **블록의 실제 코드와 줄별 해설**: 블록 설명 창의 예시 그림 아래에 그 블록을 구현한 실제 코드를 전부 싣고(파일 경로 · 커밋 · 실제 줄 번호) 줄마다 «무엇을 · 어떻게 · 왜» 를 적는다. import 줄 · 빈 줄 · 주석 줄(문서 문자열 포함)은 표에 싣지 않는다. 같은 꼴이 반복되는 줄은 대표 줄 하나에만 해설을 쓰고 그 해설이 적용되는 줄을 적는다(«L10 · L12 · L14», «L44 ~ L51»). 나머지 줄은 대표 줄 번호만 가리킨다. 전/후가 있는 블록은 기준판 코드와 이 판 코드를 따로 싣고 이 판에서 새로 생기거나 바뀐 줄을 표시한다. 코드가 없는 블록은 까닭을 한 줄 적는다(2026-11-21 사용자 지시 «실제 코드도 볼 수 있도록 하고 해당 코드를 한 줄씩 리뷰하여 각 한 줄 마다 무엇을 어떻게 왜 사용한 코드인지 설명 추가해» · «Import, 아무것도 없는 줄, 주석은 아예 코드 설명에서 제외»).
- **코드 이해용 그림**: 수식이 든 줄과 모델 관련 줄(layer · optimizer · loss 등)에는 그 줄 옆에 이해용 그림을 붙인다. 그 밖의 줄에는 붙이지 않고, 참고 줄은 대표 줄의 그림을 함께 쓴다. 이 그림도 생성형으로만 만든다(2026-11-21 사용자 답 «생성형으로만» · «수학적 수식 관련 코드나 AI 모델 관련 코드에만 이해용 이미지를 첨부하면 된다». 수식이 들어 있어도 `skills/figure/SKILL.md` 의 «수식 포함은 코드로» 보다 이 항이 우선한다).
- **선택 근거와 참고 자료**: 코드의 class · def 단위마다 해설 아래에 «선택 근거와 참고 자료» 를 펼쳐 볼 수 있게 둔다. 줄이나 개념 단위로 두지 않고, class 안의 메서드는 그 class 에 묶는다. 근거에는 그 class 나 def 의 구조 · 방법을 왜 골랐는지를 대안과 견주어 적고, 참고 자료에는 근거가 된 논문 · 기술 보고서의 제목 · 연도 · 링크 · 한 줄 요지를 적는다. 논문은 인용 검증(citation-verifier, `rules/agent-routing.md` 라우팅 3.6)을 거친 것만 싣고 검증 결과와 날짜를 함께 적는다(2026-11-21 사용자 지시 «왜 해당 요소를 선택했는 지에 대한 근거와 그에 대한 레퍼런스 논문이나 자료를 펼치기로 볼 수 있도록» · «선택 근거과 참고 자료는 class나 def 단위로만 하면 돼 그래야 논문이나 기술 리포트 단위로 인용한 근거가 생기지. 개념 단위가 아니라»).
- **그림 보관과 재사용**: 블록 예시 그림과 코드 이해용 그림은 만들기 전에 온톨로지에서 같은 설명에 쓸 수 있는 그림을 먼저 찾고, 있으면 세션이 판단해 그대로 쓴다. 없어서 새로 만든 그림은 검수 뒤 온톨로지에 보관한다. 개념 그림은 `knowledge/concepts/`, 블록 예시 그림은 `knowledge/<프로젝트>/figures/` 가 자리다(절차: `skills/figure/SKILL.md` § 그림 보관과 재사용). 계획서 보고에는 재사용한 그림과 새로 만든 그림의 목록을 싣는다(2026-11-21 사용자 지시 «생성된 이미지는 온톨로지에 보관해놨다가 나중에 동일한 설명에 사용 가능한 건 재활용»).
- **메모 기능**: 사용자가 계획서 위에 질문 · 의문 · 틀린 곳을 적어 두면 세션이 읽는 기능이다. 페이지 저장소를 쓴다(`artifact-capabilities` 스킬의 `db`).
  - 메모 모드를 켜면 페이지 어디든 누르거나 글자를 골라 그 자리에 메모한다. 색별 용도는 사용자가 주관식으로 정한다.
  - «작성 완료» 는 저장만 한다. 우하단 «메모 목록» 오른쪽의 «메모 복사» 단추가 새 메모 수와 번호를 적은 안내 글을 클립보드에 복사하고, 사용자가 그 글을 세션 채팅에 붙여 넣는다. 안내 글에 메모 내용은 담지 않는다.
  - 복사한 메모는 지우지 않고 «복사함 날짜» 만 표시한다. 복사한 메모에는 댓글처럼 «추가 메모 N회» 를 단다.
  - 메모를 단 자리에 «메모 N» 을 표시하고 누르면 그 자리의 메모 내역이 펼쳐진다. 메모 목록의 «위치로» 는 그 블록의 설명 창까지 열고 이동한 뒤 메모를 펼친다.
  - 검토 상태 «검토 중(주황) · 검토 완료(초록)» 를 우상단에 따로 표시한다.
  - **삭제 전 백업**: 아티팩트를 지우면 메모 저장소도 사라진다. 위 «확인 뒤 삭제» 전에 메모 저장소를 세션 임시 폴더에 파일로 먼저 백업한다. 삭제가 모바일 모드로 미뤄졌으면 모드를 끈 뒤 사용자가 지시해 실제로 지우기 직전에 다시 백업한다(그사이 메모가 늘 수 있다).
  - **세션이 메모를 읽는 절차**: 사용자가 안내 글을 붙여 넣거나 확인 팝업에 «메모를 썼다» 고 답하면, 세션은 ArtifactData 로 그 계획서의 `memos` 컬렉션을 읽어 메모마다 답한다. 페이지에서 세션으로 보내는 전송 기능은 두지 않는다(2026-11-19 사용자 지시 «메모 전송 눌렀을 때, 어쩌피 해당 세션 전송 안 되니까 없애도록», 전송은 성공해도 세션이 깨어나지 않았다).
- **견본**: `skills/figure/templates/training-plan-skeleton.html` 을 세션 임시 폴더로 복사해 `<title>` 과 `PLAN` 자료 객체의 `채움[Fnn]` 자리만 채운다. 위 항목(설명 세 줄 · 구조도 블록 · 달라진 블록 표시 · 전/후 토글 · 메모 · 실제 코드와 줄별 해설 · 코드 이해용 그림 · 선택 근거와 참고 자료)과 그림 크기 조절은 견본의 코드에 들어 있으므로 다시 짜지 않는다. 코드와 줄별 해설은 견본의 `plan-code` JSON 칸에 채운다. 채운 뒤 `python3 -I ~/.claude/skills/figure/templates/check_template.py --filled <계획서.html>` 이 통과해야 한다. 게시할 때는 `capabilities: {db: {}, user: {}}` 를 선언하고 실제 그림은 함께 올리는 파일로 둔다(2026-11-19 결정 팝업 «뼈대 견본을 하네스에 새로 둠», 의뢰서 `intent/2026-11-19-plan-html-skeleton-and-grok-overwrite.md`). `--filled` 검사는 빈 그림 칸도 실패로 본다(같은 의뢰서 개정 2, 결정 팝업 «빈 그림 칸이 있으면 실패»). 코드 칸의 빠진 해설 · 잘못된 참고 · 실린 import · 빈 줄 · 주석 줄 · 빈 이해용 그림도 실패로 본다(같은 의뢰서 개정 3). class · def 줄의 빠진 선택 근거 · 참고 자료 · 검증 기록도 실패로 본다(같은 의뢰서 개정 4 · 5).

## § 학습 목표 표 (HARD GATE — 2026-08-28 사용자 지시)

학습·대형 추론 발사 명령서(`launch-set.sh launch` 기본형·pool 런처·개별 발사 전부)를 출력하기 **직전**에 아래 표를 먼저 쓴다. 표가 없는 발사 명령서는 미완성이라 출력하지 않는다(2종 세트와 같은 급).

> **집행 주체는 main의 "명령서 출력 금지"다.** PreToolUse 훅 `train-launch-warn.sh`는 학습 발사 명령을 감지해도 경고만 출력하고 차단하지 않는다(2026-09-13 사용자 결정 «경고만» 유지. 훅으로 승격하는 안은 보류). 이 절의 HARD GATE는 그래서 훅이 아니라 main이 스스로 명령서를 내지 않는 것으로 성립한다. main 이 직접 발사할 때(§ main 의 tmux 직접 발사)도 같다. 표를 사용자에게 먼저 보이지 않았으면 발사하지 않는다.

| # | arm/run | 축 | 목표(한 줄) |
|---|---|---|---|
| 1 | {arm 슬러그} | {비교 축} | {이 run 하나가 검증하는 것} |

- 마지막 줄에 **"총 N건 (축별 내역)"** 을 적는다. 예: "총 6건 (해상도 2·증강 3·통제 1)".
- **통제 arm**은 "무엇의 기준선인지"를 목표로 적는다. 예: "res640 승격판의 기준선(증강 off)". "baseline"만 적으면 미완성이다.
- 목표는 arm 이름·override 목록을 옮겨 적는 것이 아니라 **그 run이 없으면 무엇을 판단할 수 없는지**를 한 줄로 적는다.
- **드라이런 완료 보고**에도 같은 표를 붙인다(발사 승인 판단은 드라이런 보고 시점에 이루어진다).
- 표의 행 수와 명령서의 run 수가 다르면 명령서가 틀린 것이다. 발사 전 대조한다.

**근거 (2026-08-28)**: 한 프로젝트의 여러 판 발사 명령서를 받은 사용자가 "각 실험 목표를 한 줄씩 요약하고 총 몇 건인지"를 따로 요구했다. arm 이름·override 목록만으로는 무엇을 검증하는지 읽히지 않아 발사 승인 판단이 되지 않았다.

## § 학습 와쳐 부착 (MANDATORY — 2026-08-15 사용자 지시)

AI 모델 학습이 발사되면(사용자 직접 발사 포함) **와쳐를 부착**한다 — 템플릿: `~/.claude/tools/train-watcher/train-watcher.sh` (재사용 표준, 프로젝트 복제 금지·인자로 재사용).

- 동작: 학습 PID 감시 → 종료 시 로그 완료 마커 확인 → **test eval 자동 실행** → 최종 보고(markdown 표 포함) 저장 + **ntfy로 사용자 알림**. 마커가 없으면(비정상 종료 의심) eval을 돌리지 않고 알림만 한다.
- **2종 세트 표준 발사 시퀀스 (2026-08-19 실측 검증)** — memguard의 exec 체인 덕에 백그라운드 발사 직후 `$!`가 그대로 학습 프로세스 PID로 유지된다(nohup→memguard-run→systemd-run --scope 전부 fork 없는 exec, scope 검증 완료):
  ```bash
  # 기본형 (2026-08-25 — 증거 파일까지 한 번에):
  bash ~/.claude/tools/train-watcher/launch-set.sh launch --name {슬러그} --log train.log \
    --done-regex '{완료 마커}' --eval-cmd '{eval 명령}' --title {슬러그} \
    --expect '{학습 스크립트 파일명 ERE, 예: train\.py}' -- {학습 명령}
  # state·와쳐 로그 기본 위치(2026-10-06): <프로젝트 뿌리>/.scratch/launch/launch-state-{슬러그}.json·watcher-{슬러그}.log (+ .json.lock). 뿌리는 git 최상위(저장소가 아니면 현재 폴더), 프로젝트 최상위에는 만들지 않는다. --state·--watcher-log 로 직접 줄 수 있다.
  # 와쳐만 재부착: bash ~/.claude/tools/train-watcher/launch-set.sh reattach <뿌리>/.scratch/launch/launch-state-{슬러그}.json --confirm-eval '{eval 명령 원문}'
  ```
  손으로 풀어 쓴 `nohup … > train.log 2>&1 &` 발사 시퀀스는 쓰지 않는다(화면을 비우는 리다이렉트·nohup 단독 발사 금지, § 학습 세션·체크포인트 배치). 발사는 tmux 창 안의 `launch-set.sh launch` 로만 한다.
  (launch-set.sh 가 memguard-run.sh 의 `exec` 체인으로 학습 PID 를 `memguard-{슬러그}-<pid>.scope` cgroup 안에 두고, `launch-set.sh verify` 가 이 scope 를 커널 증거로 쓴다.)
  (인자·종료 코드는 각 스크립트 헤더가 정본. memguard preflight 거부 시 watcher가 "발사 거부"로 별도 판정한다 — 크래시와 구분.)
  - **심사 시각 점검 보고서 기록 (2026-10-12, `intent/2026-10-12-reject-review-design-check.md`)**: `--intent <경로>` 를 주면 `launch-set.sh` 가 같은 경로에서 `.md` 를 뗀 `<이름>.review.md` 를 찾고(`--design-review <경로>` 로 직접 줄 수도 있다), 있으면 state 에 `design_review`·`design_review_sha256` 을 적는다. 링크는 거부(64)하고, 없으면 표준에러에 경고 한 줄만 내고 발사는 진행한다(차단 아님).
  - `verify` 는 intent 항목 옆에 design_review 항목을 참고(⚠)로만 보이며 PASS/FAIL 에 넣지 않는다. 새 실험 차수·새 판 설계에만 해당하고 승인된 설계의 재개·시드 추가·같은 설정 재발사는 면제다(정본 `rules-lazy/design-review-check.md`).
- eval 자동 실행은 code-execution.md "실행은 사용자 직접"의 **명시 예외**(2026-08-15 사용자 지시 — 검증 목적 실행 계열). 와쳐는 학습을 새로 띄우거나(재학습) 데이터를 바꾸지 않으며 학습 프로세스를 절대 죽이지 않는다. 학습 발사 자체는 § main 의 tmux 직접 발사 조건에서만 main 이 한다(2026-09-29). 예외는 사용자가 승인한 대기 목록의 다음 판을 와쳐 종료 훅(`--on-exit`)이 올리는 경우 하나다(§ 대기 목록 자동 발사, 2026-10-01).
- 과거 실사고 3건(pipefail+grep -q SIGPIPE 오판·ps|grep self-match·크래시를 완료로 오판해 epoch3 eval)이 스크립트 설계 제약 1~4로 인코딩돼 있다 — 수정 전 헤더 필독.
- **부착 증거 게이트 (HARD GATE — 2026-08-25 승격, 같은 날 구조화)**: 세션이 와쳐 부착을 잊는 사고가 반복돼 두 지점에서 차단한다. Codex·Grok 교차감사(2026-08-25)가 "채팅에 적은 PID는 위조·오판 가능(살아있는 무관 PID·`kill -0 $$`·옛 로그, 표준 시퀀스에 WATCHER_PID 캡처도 없음)"을 지적해 증거를 **스크립트 산출물**로 바꿨다.
  1. **명령서 작성 시점**: 학습·대형 추론 발사 명령서의 기본형은 `~/.claude/tools/train-watcher/launch-set.sh launch --name … --log … --done-regex … --eval-cmd … --title … -- {학습 명령}`(memguard+와쳐 동시 기동 + `<뿌리>/.scratch/launch/launch-state-{슬러그}.json`에 nonce·PID·/proc argv 기록). 손으로 풀어 쓴 nohup 시퀀스 명령서는 허용하지 않는다(미완성이라 출력하지 않는다). 러너 스크립트(`scripts/runners/LAUNCH_*.md` 관례 포함) 신설·수정 시 동일.
  2. **발사 보고 시점**: "발사 완료" 보고에는 `bash ~/.claude/tools/train-watcher/launch-set.sh verify <state 경로>`(기본 `<뿌리>/.scratch/launch/launch-state-{슬러그}.json`)의 **출력 원문**(state 권한·host·boot_id·학습 PID 생존·starttime·exe·memguard scope·expect 패턴·와쳐 PID 생존·starttime·argv·감시 대상·로그 nonce, **판정 항목(chk) 전부 ✅** — `⚠` 로 찍히는 참고 항목(**학습(train) argv sha·expect 토큰**만 — setproctitle 로 바뀔 수 있어 판정 제외)은 그대로 첨부하되 PASS 조건이 아니다. **와쳐 argv sha256·와쳐 스크립트 실경로·와쳐 exe는 `chk` 항목**이라 ❌면 FAIL이다(8라운드 렌즈3: "argv sha는 참고"를 와쳐까지 확대 해석하는 오판 차단). 항목 목록의 정본은 스크립트 `cmd_verify`)을 첨부한다. 발사 명령서에는 `--expect '{학습 스크립트 패턴}'`이 필수다(더미 명령으로 PASS 받는 경로 차단). 채팅에 적은 PID 숫자·`kill -0` 결과·watcher.log 첫 줄 인용은 증거로 인정하지 않는다. VERIFY FAIL이면 완료 선언 금지(완료 게이트 원칙 6의 학습 특수화). 사용자가 직접 발사한 경우도 세션이 verify를 돌려 확인하고, state 파일이 없으면 와쳐 재부착 명령서를 낸다(학습 프로세스는 건드리지 않음). **증거의 한계(4라운드 검수 정직 표기)**: `--expect`는 argv **토큰 전체** 일치이며 호출자가 패턴과 더미 명령을 함께 정하면 통과할 수 있고, verify는 자기 state의 사후 재확인이라 손으로 쓴 state를 판별하지 못한다. 그래서 정본은 **사용자 터미널의 launch 출력 원문(LAUNCHED + VERIFY 블록)**이고(main 이 발사했으면 그 tmux 창의 `tmux capture-pane -p` 원문), 세션의 verify 출력은 그 뒤 생존 재확인이다. 발사 보고에는 `--expect` 값과 argv(masked) 줄이 실제 학습 스크립트를 가리키는지 main이 눈으로 대조한 결과를 한 줄 적는다.

## § 학습 세션·체크포인트 배치 (HARD GATE — 2026-09-13 사용자 지시, 예외 없음)

사용자 원문: «AI 학습 사항은 tmux 세션 생성해서 진행. 세션 네이밍은 각 프로젝트 별로 지정하여 프로젝트 하네스에 저장» · «체크포인트는 사용자가 지정한 로컬에 저장했다가 원하는 경우 다른 nfs 마운트나 nas, rsync 등 네트워크로 이동».

- **프로젝트 값의 자리**: `<프로젝트 루트>/.claude/train.env`. 키는 다섯이다(셋은 기본, 둘은 판 수 < GPU 묶음 배치용 선택 키).
  ```
  TRAIN_TMUX_PREFIX=<세션 접두>      # 세션 이름은 <접두><GPU 번호>. 접두는 사용자가 프로젝트마다 미리 정한다. 예: 접두 exp · GPU3 → exp3
  CKPT_ROOT=<로컬 절대 경로>          # 체크포인트가 먼저 떨어지는 곳. 네트워크 파일시스템 불가
  CKPT_REMOTE=<이동 목적지>           # 선택. 다른 NFS 마운트 · NAS 경로 · user@host:/path
  DDP_READY=1                        # 선택. DDP 준비(판 수별 GPU 배치 기본값의 주의 사항 1·2) 충족 선언. 없으면 판당 1장
  PROP_BATCH_READY=1                 # 선택. 기종이 다른 카드의 비례 짝 구현(주의 사항 4) 선언. 없으면 비례 짝 배치를 제안하지 않는다
  ```
  파일이 없으면 main 이 발사 명령서를 내기 전에 앞의 세 줄(TRAIN_TMUX_PREFIX·CKPT_ROOT·CKPT_REMOTE)을 만들라고 안내한다. `/project-init` 스캐폴드에 들어 있다. **접두는 사용자가 미리 지정한 값만 쓴다**(2026-10-02 사용자 지시 «<접두>를 사용자가 미리 지정하도록 해»). main 이 접두를 지어내거나 다른 프로젝트의 접두를 빌려 쓰지 않으며, 지정이 없으면 발사 전에 묻는다.
- **세션 번호 = GPU 번호, 같은 GPU 는 창으로 나눈다 (모든 프로젝트 공통 — 2026-10-02 사용자 지시)**.
  - 세션 이름은 `<접두>N` 이고 **N 은 그 판이 쓰는 GPU 번호**다(GPU0 → `<접두>0`). 세션은 서버의 GPU 수(서버 등록부 `gpu.count`)만큼만 쓴다. 그 밖의 번호로 새 세션을 만들지 않는다.
  - 그 GPU 의 세션이 없을 때만 `tmux new-session -d -s <접두>N` 으로 만들고, 있으면 그 세션을 쓴다.
  - **같은 GPU 에 여러 판**을 올릴 때는 새 세션을 만들지 않고 `tmux new-window -d -t <접두>N:` 으로 창을 더해 `<접두>N:1` · `<접두>N:2` 로 나눈다. 한 GPU 에 판을 겹쳐도 되는지는 프로젝트 GPU 규칙이 따로 정한다(이 항은 세션 배치만 정한다).
  - 한 판이 여러 GPU 를 쓰는 경우(DDP 등)의 세션은 정해져 있지 않다. 발사 전에 사용자에게 묻는다.
  - 이 항이 2026-09-16 · 09-23 의 «세션 하나에 판 하나, 기존 세션에 창을 만들지 않는다»를 **대체한다**(번복).
  - **도는 판을 옮기는 법**: 다른 세션에서 도는 판은 `tmux move-window -d -s <옛 세션>: -t <접두>N:` 으로 옮긴다. 프로세스는 죽지 않고 launch-set state 와 와쳐는 세션 이름에 기대지 않아 그대로 돈다. 옮긴 뒤 빈 세션을 닫는 일은 아래 «세션·창 종료 재확인»을 따른다.
- **tmux 세션**: 발사 · 자동 투입 대기기 · 평가 사슬은 전부 `<접두>N` 세션의 창 안에서 시작한다. main 은 발사 명령서에 `tmux new-session -d -s <접두>N` 과 그 창 안에서의 실행을 함께 적고(직접 발사할 때는 그대로 실행하고), 세션 이름이 `<접두>[0-9]+` 가 아니면 명령서를 내지도 발사하지도 않는다. setsid · nohup 단독 배경 발사는 금지다(2026-09-07 실사고: 창 밖에서 띄운 판을 사용자가 멈춘 줄 알았다).
- **화면 출력을 지우는 리다이렉트 금지 (2026-09-28 사용자 지시, 한 학습 세션 경유. 규칙만이고 강제 코드 없음)**: `exec >> "$LOG" 2>&1` 처럼 셸의 표준출력·에러를 로그 파일로만 돌려 tmux pane 화면을 비게 만드는 방식은 금지다. 로그 저장이 필요하면 `tee`(또는 이에 준하는 이중화)로 화면 출력과 파일 저장을 동시에 한다. tmux 에 붙었을 때 학습이 죽었는지 살았는지가 항상 화면만으로 보여야 한다.
- **launch-set.sh 의 창 발사 출력 배치 (2026-09-29 사용자 결정 «1번»)**: 창(tty)에서 부르면 학습의 표준출력은 그 창으로 곧바로 가고, 표준에러만 `--log` 파일로 간다. 진행 막대가 진짜 터미널에 그려져 창 크기를 따라가고, 막대 다시 그리기가 로그를 채우지 않는다(실측: 표준출력까지 로그로 받던 판은 40분에 14.4MB·9.7만 줄, 바꾼 뒤 시험은 251바이트). `--log` 파일 내용(경고·예외 추적)은 발사 확인 뒤 같은 창에 따라 흘린다.
  - **완료 마커가 표준출력이면 `--done-log` 필수**: 와쳐는 기본으로 `--log` 에서 완료 마커를 찾는데, 표준출력으로 찍히는 줄은 거기 남지 않는다. 프로젝트가 따로 쓰는 로그 파일을 글롭으로 준다(예: `--done-log '<ckpt>/<exp>/train_run_*/train.log'`). 와쳐는 학습 시작 뒤 수정된 파일 중 가장 최근 것에서 찾는다. 글롭은 그 판에만 맞게 좁힌다(같은 폴더를 쓰는 다른 판이 있으면 그쪽을 집을 수 있다).
  - **창을 닫으면 학습이 죽는다**: 표준출력이 창이라, 창 자체가 없어지면(창에서 `exit`·Ctrl+D, `tmux kill-session`·`kill-pane`, tmux 서버 종료) 다음 출력에서 입출력 오류로 죽는다. 빠져나오기(detach, Ctrl+b d)는 무관하다(시험 확인). 그래서 아래 세션 종료 재확인 규칙을 둔다.
  - tty 가 없는 곳(Bash 도구 등)에서 부르면 종전처럼 표준출력·에러 모두 `--log` 로 간다.
- **★tmux 세션·창 종료는 매번 사용자 재확인 (2026-09-29 사용자 지시)**: 사용자 원문 «혹시 모르니 tmux 세션 종료할 때는 사용자한테 꼭 재차 확인한다는 내용을 하네스에 넣어». main·subagent 는 tmux 세션이나 창을 끝내는 어떤 조작도(`tmux kill-session`·`kill-pane`·`kill-server`, 창에 `exit`·`C-d` 보내기, 세션 정리 스크립트) 하기 전에 대상 세션 이름과 그 안에서 도는 것(`tmux capture-pane -p` 로 확인)을 적어 사용자에게 다시 묻고, 답을 받은 뒤에만 한다. 앞선 승인·이전 턴의 지시·일괄 정리 요청이 있어도 대상마다 다시 확인한다. 시험용 세션이 필요하면 처음부터 명령이 끝나면 스스로 닫히게 만든다(`tmux new-session -d -s <이름> '<명령>'`).
- **체크포인트는 로컬 먼저**: 학습 명령에 `CKPT_ROOT` 를 그대로 넘긴다. main 은 명령서를 내기 전에 `CKPT_ROOT` 가 있고 쓸 수 있으며 파일시스템이 로컬(nfs · nfs4 · cifs · smb3 · smbfs · fuse.sshfs · 9p · fuse.rclone · afs · ceph · glusterfs · lustre 가 아님)인지 `df --output=fstype` 으로 확인하고, 아니면 명령서를 내지 않는다(2026-09-08 실사고: 판 네 개가 1.65 GB 체크포인트를 NFS 에 동시에 쓰다 40분 정지). `CKPT_ROOT` 아래 구조는 원격과 같게 두어 폴더째 옮기면 원래 경로가 되게 한다.
- **체크포인트 저장 두 가지 (MANDATORY — 2026-09-29 사용자 지시, 한 학습 세션 경유, 모든 학습)**: 사용자 원문 «"무조건" 기준이 되는 val metric의 topK 및 last.ckpt까지 저장되도록 하네스 매니저에게 지정하도록 해 top K의 k는 사용자가 지정하도록 하고» · 보충 «last.ckpt 저장은 매 에폭마다, val best는 val 주기마다 저장되도록 해야 해». 저장 주기는 두 갈래로 나뉜다.
  1. **last.ckpt 는 매 에폭 끝에 갱신한다**(검증이 도는 에폭이든 아니든). 검증 주기(`check_val_every_n_epoch`·`ckpt_period`)와 분리한다. 중단·재개로 잃는 진행분이 에폭 하나를 넘지 않게 하려는 것이다. 실사고(09-29): 한 프로젝트의 러너는 last.ckpt 가 검증 주기인 5에폭마다만 갱신돼, GPU 를 비울 때 판마다 다음 5에폭 경계까지 최대 수 시간을 기다려야 했다. Lightning 이면 감시 지표용 ModelCheckpoint 와 따로, `on_train_epoch_end` 에서 `trainer.save_checkpoint(<판 폴더>/last.ckpt)` 를 부르는 콜백을 하나 둔다(모든 순위에서 불러도 파일은 순위 0 만 쓴다). `ModelCheckpoint(save_last=True, save_top_k=0, ...)` 설정에 기대지 않는다. 그 설정은 버전마다 달리 동작한다(2.5.6 은 매 에폭 쓰지만 2.6.0 은 그 스텝에 top-K 저장이 없으면 last 를 건너뛰어 `model_checkpoint.py:495` 한 번도 쓰지 않는다). 09-30 CPU 시험(4에폭, 검증 2에폭마다): 설정 방식은 2.6.0 에서 last.ckpt 0회, 콜백 방식은 2.5.6·2.6.0 모두 매 에폭 저장했고 그 파일로 재개하면 다음 에폭부터 이어졌다.
  2. **기준 val 지표(감시 지표 monitor)의 top-K(best) 는 검증이 도는 주기마다 판정·저장한다**(검증 없는 에폭에는 판정할 값이 없다). K 는 사용자가 정한다. 명령서에 K 가 명시돼 있으면 그 값을 쓰고, 없으면 발사 전에 사용자에게 묻는다. 임의 기본값으로 조용히 정하지 않는다.
  - 둘 중 하나라도 설정에서 빠진 명령서는 미완성이라 내지도 발사하지도 않는다. main 은 발사 전에 설정 파일·러너에서 두 항목을 확인하고, 명령서 머리의 `CKPT_ROOT` 줄 옆에 «last 매 에폭 · top-K=<값>(<지표>)»를 적는다. 프로젝트 러너 수정은 그 프로젝트 세션의 몫이다.
  - **띠 진행 표시(2026-10-22 사용자 결정 «진행 파일 규약»)**: 하네스 띠는 명령줄 `max_epochs=N` 과 판 폴더의 Lightning `last.ckpt` 로 «17/60에폭» 을 보인다. 이 둘이 없는 판(자체 프레임워크·detectron2 등)은 학습 코드가 판 전용 폴더(또는 그 `checkpoints/`)에 `band_progress.json` 을 `{"done": 끝낸 에폭 수, "max": 최대 에폭 수}` 로 쓰고 에폭마다 갱신한다(정수, 0 ≤ done ≤ max ≤ 100000, 4 KiB 이하, 심볼릭 링크 금지). 판 폴더는 프로세스가 연 파일의 폴더나 명령줄로 넘긴 절대 경로 파일(예: 그 판의 `spec.json`)의 폴더여야 수집기가 찾는다. 여러 판이 같이 쓰는 폴더(공용 코드·설정 폴더)에는 두지 않는다: 그 폴더를 인자로 쓰는 모든 판에 같은 값이 붙는다. 이 파일이 있으면 명령줄·체크포인트 값보다 앞선다. 띠의 «last» 칸(재개용 체크포인트가 있는가)은 선택 키 `"last": true|false` 로 밝힐 수 있고(2026-10-22 사용자 결정 «둘 다»), 키가 없으면 판 폴더의 `last.ckpt`·`last-vN.ckpt`·`last.pth`(detectron2) 가 있는지로 판정한다. 재개용 파일을 다른 이름으로 쓰는 판은 이 키를 쓴다. 공용 폴더에 두지 않는 원칙은 `last.pth` 에도 같다. 반복 단위로 도는 판은 에폭으로 바꿔 적는다(끝낸 반복 ÷ 에폭당 반복의 내림). 정본: `scripts/band_server_collect.py` `read_progress`.
  - **확인은 설정이 아니라 실행 중 파일로 한다**(2026-09-30 사용자 결정): 발사 뒤 첫 두 에폭이 끝날 때 판 폴더의 last.ckpt 수정 시각이 에폭마다 바뀌는지 본다(파일 안 `epoch` 값이 방금 끝난 에폭인지로 대조한다). 설정이 맞아 보여도 이 확인 없이 «매 에폭 저장»이라고 적지 않는다. 안 바뀌면 판을 건드리지 말고 사용자에게 알린다.
- **원격 이동은 학습이 끝난 뒤 사용자 직접**(데이터 변경). 명령서 기본형은 아래이고 다른 NFS 마운트 · NAS · 원격 호스트 어느 쪽이든 `CKPT_REMOTE` 만 바꾼다. 옮긴 뒤 원본 삭제는 전수 대조 뒤에만 한다.
  ```
  rsync -a --partial --info=progress2 "$CKPT_ROOT/<판 폴더>/" "$CKPT_REMOTE/<판 폴더>/"
  ```
- **가중치 이관 위치·방식 (2026-10-30 사용자 결정 W1 «이관 위치 · 방식만 규칙화, 실행은 매번 승인»)**: 서버 등록부에 `paths.weights_local`·`paths.weights_archive` 가 있는 서버에 적용한다(사용자 원문: `knowledge/harness/rules-project-server-history-2026-11-10.md` § background-task). 원칙만 규칙으로 고정하고 옮기기·지우기는 여전히 데이터 변경이라 건마다 사용자 승인을 받는다.
  1. **가중치 이관**: 그 서버에서 로컬(`paths.weights_local` 등)의 가중치를 비울 때 목적지는 `paths.weights_archive` 아래이고 원래 상대 경로를 그대로 둔다(예: `<weights_local>/<프로젝트>/<판>` → `<weights_archive>/<프로젝트>/<판>`). 세션은 이관 스크립트를 파일로 쓴다(rsync 복사 → `diff -r` 또는 파일 수·크기 전수 대조 → 일치할 때만 원본 삭제, 불일치면 원본을 두고 멈춤). 실행은 tmux `data` 세션의 창에서 하거나, 각 세션이 자기 data 세션(이름은 각자 정한다, 예: `data-<프로젝트>`)을 새로 만들어 그 안에서 해도 된다(2026-10-30 사용자 지시 «tmux data 세션이 아니더라도 각자의 data 세션을 만들어도 된다고 해», 만들 때 따로 묻지 않는다). 이 세션은 학습 세션이 아니므로 «세션 번호 = GPU 번호» 규칙의 대상이 아니다. 실행 전에 «대상 경로 · 크기 · 목적지» 후보 표를 사용자에게 올려 승인받는다. 같은 사이클에 사용자가 그 세션에서 직접 지시한 대상은 승인된 것으로 본다.
  2. **드라이런 체크포인트**: 드라이런(속도·메모리·배선 확인용 짧은 판)이 끝나면 그 판이 남긴 체크포인트를 바로 지우는 것이 원칙이다. 드라이런 완료 보고에 «지울 경로 · 크기» 한 줄을 붙여 승인받고 지운다. 본 판의 재개·비교에 쓸 체크포인트는 드라이런 산출물이 아니므로 대상이 아니다.
  - 학습 중인 판의 폴더는 어느 쪽 대상도 아니다(학습이 끝난 판만). tmux `data` 세션·창 종료는 위 «tmux 세션·창 종료는 매번 사용자 재확인»을 따른다.
- **명령서에 남기는 것**: 발사 명령서 머리에 tmux 세션 이름 · `CKPT_ROOT` · 그 파일시스템 종류(`df --output=fstype` 출력 원문) · 체크포인트 저장 두 가지(last 매 에폭 · top-K 값과 지표)를 적는다. 발사기 자체의 강제 검사는 두지 않았다(2026-09-13 사용자 지시 «규칙만 추가»). 강제로 올릴지는 사용자 결정 항목이다.

## § main 의 tmux 직접 발사 (2026-09-29 사용자 지시)

사용자 원문: «tmux 세션에 학습 발사(실행)하는 것도 클로드 코드 세션이 못 하고 있는데 이걸 수정해서 tmux 에 학습 올리는 건 가능하도록 수정해». `rules/code-execution.md` 의 «main 의 tmux 학습 발사» 실행 예외다. 안전장치는 새로 만들지 않고 위 발사 세트를 그대로 상속한다.

- **누가·언제**: main 세션만 발사한다. subagent·teammate 는 명령서만 쓴다. 사용자가 이번 작업 사이클에 발사를 지시한 학습만 올리며, main 이 스스로 판을 늘리지 않는다.
- **발사 전**: 명령서를 낼 때와 같은 게이트를 모두 통과한다. 목표 표를 사용자에게 먼저 보이고, GPU 는 사용자 배정과 프로젝트 GPU 규칙대로 고르며, `train.env` 의 세션 접두와 `CKPT_ROOT` 로컬 여부(`df --output=fstype`)를 확인한다. 세션은 그 판의 GPU 번호 세션이고, 같은 GPU 의 다른 판은 그 세션의 창으로 나눈다(§ 학습 세션 «세션 번호 = GPU 번호»).
- **방법**: Bash 도구에서 `nohup`·`setsid`·`&` 로 바로 띄우지 않는다. 도구가 만든 셸은 tty 가 없어 화면에 아무것도 안 보인다. 반드시 tmux 창 안에서 돌린다.
  ```bash
  tmux has-session -t <접두>N 2>/dev/null || tmux new-session -d -s <접두>N -c <프로젝트 루트>   # N = GPU 번호
  tmux send-keys -t <접두>N 'bash ~/.claude/tools/train-watcher/launch-set.sh launch --name … --log run.log [--done-log <프로젝트 로그 글롭>] … -- <학습 명령>' Enter
  ```
  같은 GPU 의 둘째 판부터는 `tmux new-window -d -t <접두>N: -c <프로젝트 루트>` 로 창을 만들고 `-t <접두>N:<창 번호>` 로 보낸다(`tmux new-window` 가 권한 규칙에 막히면 다시 시도하지 않고 사용자에게 올린다). 이미 있는 세션을 쓸 때는 `tmux capture-pane -p -t <세션>` 으로 창이 유휴인지 먼저 본다. 도는 판 위에 키를 보내지 않는다. 완료 마커가 표준출력으로 찍히는 프로젝트는 `--done-log` 를 반드시 준다(§ 학습 세션 «launch-set.sh 의 창 발사 출력 배치»).
- **발사 완료 증거**: 발사 뒤 `tmux capture-pane -p -t <접두>N` 으로 창의 LAUNCHED·VERIFY 블록 원문을 읽는다. 따로 `launch-set.sh verify <state>` 도 돌려 원문을 보고에 붙인다. 학습이 발사 확인보다 먼저 막대를 그리기 시작하면 창의 VERIFY 블록 사이에 막대 줄이 섞일 수 있으니, 이때는 따로 돌린 verify 원문이 정본이다. 창에 학습 로그가 실제로 흐르는지도 같은 방법으로 확인한다(화면 공백 금지). 셋 중 하나라도 없으면 «발사 완료»라고 말하지 않는다.
- **여전히 사용자 몫**: 도는 학습을 멈추거나 죽이는 일(사용자 지시가 있을 때만 main 이 한다. 발사 권한에 딸려 오지 않는다), 체크포인트 원격 이동·삭제, 데이터 변경·전처리, 환경 변경(`uv add` 등), 배포, push·pull.
- **훅**: `scripts/train-launch-warn.sh` 는 계속 경고만 낸다. 허가는 Claude Code 권한 설정이 맡고 훅은 허가를 주지 않는다.
- **전제 조건: 사용자가 넣는 권한 규칙 (2026-09-29 실측)**: 이 문서만으로는 발사가 안 된다. 자동 모드 분류기는 `tmux send-keys` 발사를 «[Auto-Mode Bypass]» 로 막고, 세션이 허용 규칙을 스스로 넣으려는 시도도 같은 사유로 막는다. 사용자가 `~/.claude/settings.json` 의 `permissions.allow` 에 tmux 발사 규칙을 직접 넣어야 통과한다. 막히면 main 은 다른 도구·분할·따옴표로 다시 시도하지 않는다. 사용자에게 넣을 규칙을 보여 주고 멈춘다. 2026-09-29 사용자가 넣은 규칙(넓은 쪽 선택): `Bash(tmux new-session *)` · `Bash(tmux send-keys *)` · `Bash(tmux capture-pane *)` · `Bash(bash ~/.claude/tools/train-watcher/launch-set.sh *)`. 같은 날 시험 창에서 새 창·키 보내기·화면 읽기·창 안 `launch-set.sh`·직접 `launch-set.sh` 다섯 경로가 모두 통과했다. 보내는 문장 안의 `$((…))` 같은 셸 전개는 하네스 쓰기 검사 훅이 따로 막으니 발사 문장은 평범하게 쓴다.

## § 대기 목록 자동 발사 (2026-10-01 사용자 결정)

사용자 원문: «미리 줄 세우는 거보다 어쩌피 각 학습에 와쳐 무조건 달아놓기로 했으니 학습 완료되는 gpu에 다음 실험 올리는 걸로 하는 게 더 좋을 거 같은데? 진짜 VRAM 사용량 큰 실험만 예외로 H100 같은 GPU에 올리고» · «1. 판 > GPU 일 때만 2. 와쳐가 자동으로». `rules/code-execution.md` 의 «대기 목록 자동 발사» 실행 예외다. 도구는 `tools/train-watcher/launch_queue.py`(머리 주석이 명령·종료 코드의 정본)이고 의뢰서는 `intent/2026-10-01-watcher-auto-launch-queue.md` 다. 발사 세트(메모리 가드·와쳐·tmux 세션·체크포인트)는 그대로 상속한다. 배정된 GPU 의 세션 `<접두><GPU 번호>` 에(없으면 만들고 있으면 창을 더해) `launch-set.sh launch` 가 돈다.

- **언제 쓰나**: 같은 차수에 올릴 판이 쓸 수 있는 GPU 보다 많을 때만. 판이 GPU 이하이면 종전대로 main 이 직접 발사한다(판이 적을 때의 묶음 배치는 아래 «판 < GPU»).
- **목록 파일**: `<프로젝트>/.claude/launch-queue/<이름>.json`. 판마다 `id`·`purpose`(목적)·`baseline`(기준판)·`change`(변경 사항 한 줄)·`argv`(배열, `{GPU}` 치환)·`expect`·`log_dir`(절대 경로)·`vram_gb`·`cpu_cores`·`done_regex` 를 적고 필요하면 `done_log`·`eval_cmd`·`memguard_args`·`watcher_args`·`preflight_args`·`progress_regex`·`intent` 를 더한다. 목록 순서가 발사 순서다. VRAM 이 큰 판은 `vram_gb` 만 정확히 적으면 들어가지 않는 GPU 를 건너뛰어 VRAM 이 큰 카드가 빌 때 올라간다. `preflight_args` 는 그 판의 발사 사전검사(`launch-set.sh --preflight-args`)에 그대로 넘어간다(예: 다른 팀과 같이 쓰는 GPU 에 올릴 판은 `--util-max 100`). `--gpu`·`--vram-gb`·`--cpu-cores` 는 줄 수 없지만 `--vram-margin`·`--cpu-reserve` 는 받으므로 이 칸으로 VRAM · CPU 한도도 느슨해질 수 있다. `--sample-sec` 를 길게 주면 발사 대기 300초를 넘겨 발사 실패로 판정될 수 있다(2026-11-20 사용자 결정, 의뢰서 `intent/2026-10-01-watcher-auto-launch-queue.md` 개정 1).
- **승인 (HARD GATE)**: main 은 `launch_queue.py table <목록> --gpus …` 출력(판·목적·기준판·변경 사항·배치와 판별 실행 요약)을 사용자에게 그대로 보이고 «이대로 / 바꾸기 / 거부» 선택지를 낸다. «이대로»를 받은 뒤에만 `approve` → `start --gpus <사용자가 배정한 GPU>` 를 한다. 이 표가 그 차수의 학습 목표 표를 겸한다. **승인 표는 실행에 쓰이는 필드를 전부 보인다**: 판별 명령 인자(`argv`)·`eval_cmd`·`watcher_args`·`memguard_args`·`preflight_args`·`done_regex`·`expect`·`log`/`log_dir` 까지 기본 출력에 나와야 하며, «있음» 같은 요약만 보이거나 `--full` 을 따로 줘야 보이는 표를 근거로 «이대로»를 받지 않는다(사용자가 보지 않은 셸 명령·느슨한 한도를 승인하게 되기 때문이다, 2026-10-01 감사). 표가 이 필드를 다 보이지 않으면 `--full` 출력을 함께 보인다. GPU 번호는 사용자 배정이며 CPU·GPU 를 먼저 묻는 규칙도 그대로다.
- **재승인은 사용자만**: 승인은 목록 파일의 sha256 이다. 목록이 한 바이트라도 바뀌면 다음 발사부터 멈춘다(halted). main 은 목록을 고친 뒤 스스로 `approve` 하지 않는다. 바뀐 표를 다시 보이고 선택을 받는다. 밤사이 비정상 종료를 고치는 중에도 같다. 발사 인자를 바꿔야 고쳐지는 판은 고치지 말고 실패 사유로 남긴다. 순서만 바꿔 재승인해도 해시가 달라지므로 다시 승인이 필요하고, 재승인하면 아직 대기 중인 판의 순번은 목록 순서대로 다시 매겨진다(도는·끝난 판의 순번은 유지, 재발사로 맨 앞에 둔 판의 우선권도 유지).
- **세션이 깨어 있는 방법**: `start` 뒤 main 은 `launch_queue.py wait-event <목록>` 을 백그라운드 명령으로 걸어 둔다(기본 6,900초, 만료 rc 3 이면 다시 건다). 이벤트가 오면 처리하고 다시 건다. 안전망으로 cron 예약 점검을 하나 두어 `events <목록> --pending` 과 `status` 를 본다. `status` 가 «와쳐 없음»을 내면 그 GPU 의 사슬이 끊긴 것이라 사용자에게 알린다.
- **비정상 종료(와쳐 exit 2)**: 그 판은 `needs-fix` 가 되고 그 GPU 에는 다음 판이 계속 올라간다. main 은 `needs-fix` 이벤트를 받으면 로그로 원인을 찾는다. 경로·import·인자 오류처럼 «실행 조건» 문제일 때만 고치고, 학습 로직·손실·데이터 처리를 고쳐야 하는 실패는 재발사하지 않고 사용자에게 보고한다(실험 중 수정 금지 원칙, 원칙 8). 실행 조건 문제면 `relaunch --item ID --fix-note '<무엇을 고쳤나>'` 로 판당 한 번만 다시 올린다. 다시 실패하면 그 판만 `failed` 로 닫히고 다른 판은 계속 올라간다(사용자 결정: «실패한 그 판만 멈추고 대기 목록의 다른 판은 계속»). 같은 GPU 에서 서로 다른 두 판이 연속으로 재실패하면 그 GPU 만 빠진다(`include-gpu` 로 되돌린다).
- **GPU 를 쥔 채 남는 경우**: 와쳐 타임아웃(exit 4)·평가 시간 초과(exit 6)·와쳐 신호 중단(exit 7)과 발사 직후 실패(launch-set rc 65 등)는 학습이 살아 있을 수 있어 그 GPU 에 다음 판을 올리지 않는다. main 이 PID 사망을 확인한 뒤에만 `release --item ID --reason '<확인 근거>' [--then-next]` 로 푼다. 살아 있는 학습을 죽이는 일은 여전히 사용자 몫이다. 평가 시간 초과(6)는 프로세스를 죽이지 않고 알림만 낸 뒤 GPU 를 보류한다. 같은 판의 memguard 발사 거부가 3회(`MAX_REFUSALS`) 반복되면 `launch-failed`(outcome `refusal-cap`) 이벤트와 알림으로 그 판을 닫는다. 도는 판의 와쳐 PID 가 죽으면 `watcher-lost` 이벤트와 알림이 한 번 난다(와쳐 신호 중단 7 은 알림 후 GPU 보류). 이 알림이 오면 main 은 사용자에게 알린다.
- **기다림**: 판마다 예상 시간을 받지 않는다. 느린 GPU 가 먼저 비었을 때만, 도는 판의 진행 로그에서 남은 시간을 읽어 빠른 GPU 를 기다리는 편이 일찍 끝나면 비워 둔다(근거는 state 의 `decisions` 와 알림). 진행률을 못 읽으면 기다리지 않는다. 창 발사는 표준출력이 창으로 가므로 진행률을 읽히려면 `done_log` 에 에폭 줄이 남는 로그를 준다.
- **자동 발사 뒤에도 verify 원문을 보고에 첨부한다**: 와쳐가 올린 판도 «발사 완료»의 증거는 `launch-set.sh verify <state>` 출력 원문이다(자동 발사라는 이유로 PID·`kill -0`·로그 첫 줄로 대신하지 않는다). 자동 발사된 판의 state 경로는 `launch_queue.py status` 와 발사 알림에서 읽고, main 은 이벤트를 처리하는 턴에 verify 를 돌려 원문을 보고에 붙인다.
- **끝난 뒤 보고**: `queue-finished` 이벤트가 오면 `summary` 의 실패 판 표(판·목적·실패 단계·사유·고친 내용·GPU)를 한 번에 보고한다. 판마다 따로 보고하지 않는다.
- **정지**: `halt <목록> --reason '…'`. 이후 발사는 0건이고 도는 판은 건드리지 않는다. 다시 시작은 사용자 선택 뒤 `approve` → `start`.
- **판 < GPU**: `table`·`place` 가 `placement_table.json`(위 «판 수별 GPU 배치 기본값» 표)으로 묶음 배치를 제안한다. 프로젝트 `train.env` 에 `DDP_READY=1`(주의 사항 1·2 충족)과 비례 짝이면 `PROP_BATCH_READY=1` 이 없으면 판당 1장으로 내린다. 제안일 뿐이고 발사는 사용자가 «이대로»를 고른 뒤 main 이 한다.
- **기록**: 승인·자동 발사·재발사·해제·정지는 도구가 `oversight-append.sh` 로 감시 서명을 남긴다(주체 `watcher-queue`). 승인 뒤 프로젝트 코드가 바뀌면 발사는 하되 알림과 state 에 «승인 이후 코드가 바뀜»을 남긴다.
- **알려진 한계**: 빠른 GPU 의 와쳐가 죽으면 기다리던 GPU 가 조용히 빈다(예약 점검의 `status` 로만 드러난다). `halt` 뒤 `approve` 만으로는 다시 올라가지 않는다(`start` 필요). 시크릿 형태 검사가 `--key…` 꼴 인자 이름을 거부할 수 있다(launch-set.sh 와 같은 규칙).
