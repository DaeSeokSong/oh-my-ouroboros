# 에러 처리 규칙

> **로드 시점**: 도구 차단, MCP 오류, 외부 명령 실패, 파일 시스템 오류, 사용자 합의 미충족 감지 시 (lazy load)

---

## §1 에러 분류 표

| 분류 | 코드 | 대표 사례 |
|------|------|---------|
| (a) 도구 차단 | TOOL_BLOCKED | hook 차단 (bash-write-check.sh), permission denied, sandbox 제한 |
| (b) MCP 미연결 | MCP_UNAVAIL | Mem0·context7 MCP 응답 없음, timeout |
| (c) 외부 명령 실패 | CMD_FAIL | bash exit code ≠ 0, uv/pip 설치 실패, git 명령 오류 |
| (d) 파일 시스템 오류 | FS_ERROR | 파일 없음, 쓰기 권한 없음, 디스크 풀 |
| (e) 합의 미충족 | CONSENT_NEEDED | 사용자 승인 필요 작업 미확인 실행 시도 |

## §2 분류별 처리 절차

### (a) 도구 차단 (TOOL_BLOCKED)

**1차 대응**
1. 차단 메시지 전문 파싱 → 차단 원인 분류 (hook 정책 / permission / sandbox)
2. hook 정책 차단: `code-execution.md` § Hook 차단 시 처리 규칙 적용
   - 목적·명령을 사용자에게 설명하고 실행 여부 질문
   - 승인 시: 명령 첫 줄에 `# APPROVED «승인 발화 그대로 8자 이상»` 붙여 재실행(인용이 최근 프롬프트 로그에 있어야 통과)
3. permission denied: `chmod +x` 또는 `sudo` 가능 여부 확인 후 사용자 요청
4. **알려진 쓰기 검사 오탐 (2026-10-06 실측, 읽기 전용 명령인데 막힘)**: 따옴표 안 정규식 문자 클래스에 `<`·`>` 가 있으면 «리다이렉션», 명령 치환 안의 `<` 와 변수(`$(wc -l < $f)`)는 «셸 전개 문자», 백틱이 든 grep 패턴과 `systemctl` 낱말이 함께 있으면 «환경 상태 변경» 으로 막힌다. 명령이 정말 읽기 전용이면 트리거를 피하도록 고쳐 쓴다(예: `wc -c 파일` 처럼 리다이렉션 없이 인자로 넘기기, 패턴을 나눠 두 번 grep). 쓰기가 섞인 명령이면 위 2번(목적 설명 후 질문)을 따른다. 훅 자체 수정은 사용자 결정 사항이다.

#### Read 차단(read-once 훅) 복구 절차 (code-execution.md 이관)

`scripts/read-once.sh`(PreToolUse)는 동일 파일+동일 mtime 전체 Read를 TTL 20분간 차단한다(세션 격리 캐시). 차단 메시지("이미 읽은 파일 — 메모리에서 참조") 수신 시:
1. 내용이 이미 컨텍스트에 있으면 → 재사용 (재읽기 불필요가 정상 동작)
2. 일부만 필요하거나 재검증 목적(mem0-auto §1.5 현재 코드 우선) → **offset/limit을 지정해 Read** (부분 읽기는 캐시 미적용) 또는 Grep 사용
3. 파일이 실제로 변경됐다면 mtime이 바뀌어 자동 통과 — 차단이 반복되면 변경이 저장 안 된 것
4. compact 뒤에는 PreCompact 훅이 캐시를 비우므로 재읽기가 정상 통과한다(2026-09-08 배선. 컨텍스트에서 사라진 내용을 다시 못 읽던 문제)

**에스컬레이션 조건**
- 사용자 거부 → 대안 방법 3가지 제시 후 선택 대기
- 대안 없음 → main 에스컬레이션 + 작업 중단

**보고 형식**
```
에러: TOOL_BLOCKED
원인: {hook명 또는 permission 오류 1줄}
시도: {N회}
권고:
  1. {대안 1}
  2. {대안 2}
  3. {대안 3}
```

### (b) MCP 미연결 (MCP_UNAVAIL)

**1차 대응**
1. MCP 도구 호출 실패 감지 → 즉시 `rules-lazy/mcp-fallback.md` 로드
2. fallback 전환: Mem0 미연결 → `memory/` 파일 직접 읽기/쓰기, context7 미연결 → WebFetch로 공식 문서 직접 접근
3. 재시도: 동일 MCP 도구 최대 2회 재시도 (즉시 재시도, 지수 백오프 아님)

**에스컬레이션 조건**
- 2회 재시도 모두 실패 → fallback 전환 후 사용자 알림
- fallback 불가 → main 에스컬레이션

**보고 형식**
```
에러: MCP_UNAVAIL ({MCP 서버명})
원인: {타임아웃 / 연결 거부 / 스키마 오류 1줄}
시도: {N회}
권고:
  1. fallback 전환 ({대체 수단})
  2. MCP 서버 재시작 (사용자 직접)
  3. 해당 기능 없이 작업 계속
```

---

### (c) 외부 명령 실패 (CMD_FAIL)

**1차 대응**
1. exit code + stderr 전문 캡처
2. 에러 종류별 분기:
   - 패키지 미설치: `uv add {패키지}` 명령 제시 후 사용자 승인 요청
   - git 충돌: 충돌 파일 목록 보고 → 해결 방법 제시
   - 테스트 실패: 실패 traceback 전문 보고 → QA 에이전트 소환 검토
3. 재시도 가능 여부 판단: 멱등성 있는 명령만 1회 재시도 (동일 명령 1회, 누적 5회 에스컬레이션은 §5 표)

**에스컬레이션 조건**
- 5회 재시도 실패 → main 에스컬레이션 + 작업 중단
- 데이터 손실 위험 동반 → 즉시 중단 + main 에스컬레이션
- 원인 불명: searcher에 에러 메시지 검색 위임 (C2 조건)

**보고 형식**
```
에러: CMD_FAIL ({명령어 줄임})
원인: exit code {N} — {stderr 핵심 1줄}
시도: {N회}
권고:
  1. {즉시 대응}
  2. {우회 방법}
  3. {searcher 검색 or main 에스컬레이션}
```

---

### (d) 파일 시스템 오류 (FS_ERROR)

**1차 대응**
1. 파일 없음: 경로 오타 여부 확인 → `find`로 유사 경로 탐색 → 사용자에게 정확한 경로 질문
2. 쓰기 권한 없음: 대상 디렉토리 권한 확인 → 사용자에게 `chmod`/`chown` 요청
3. 디스크 풀: `df -h` 실행 → 용량 정보 사용자 보고 → 정리 방법 제안

**에스컬레이션 조건**
- 경로 탐색 3회 실패 → main에 정확한 경로 질문
- 쓰기 권한 해결 불가 → 작업 중단 + main 에스컬레이션

**보고 형식**
```
에러: FS_ERROR
원인: {파일 없음 / 권한 없음 / 디스크 풀 1줄}
시도: {N회}
권고:
  1. {경로 확인 방법 or chmod 명령}
  2. {대안 경로}
  3. main 에스컬레이션
```

---

### (e) 사용자 합의 미충족 (CONSENT_NEEDED)

**1차 대응**
1. 합의 필요 작업 감지 즉시 실행 중단
2. 작업 내용·영향 범위·위험도를 사용자에게 명시
3. 승인 대기 — 침묵 진행 절대 금지

**에스컬레이션 조건**
- 사용자 응답 없음 → 작업 보류 상태 유지 (타임아웃 없음)
- 사용자 거부 → 작업 취소 + 대안 제시

**보고 형식**
```
에러: CONSENT_NEEDED
원인: {합의 없이 시도된 작업 1줄}
시도: 실행 전 중단
권고:
  1. 승인 시: {작업 내용 요약}
  2. 거부 시: {대안 방법}
```

## §3 main 에스컬레이션 조건 (subagent → main)

아래 조건 중 하나라도 해당 시 즉시 main에 에스컬레이션하고 작업을 중단한다:

| 조건 | 이유 |
|------|------|
| 동일 에러 5회 재시도 실패 | 자동 복구 불가능 |
| 사용자 합의가 필요한 결정 | subagent 권한 범위 초과 |
| 데이터 손실 위험 감지 | 돌이킬 수 없는 변경 |
| 비밀 정보 노출 위험 | `secret-management.md` §3 즉시 처리 참조 |
| 인과관계 파악 불가능한 에러 | tracer mode qa 소환 필요 |
| 크로스 모듈 의존성 파괴 위험 | 아키텍처 수준 판단 필요 |

**에스컬레이션 형식 (subagent → main 보고)**
```
[에스컬레이션] {에이전트명} → main
에러 분류: {코드}
발생 위치: {파일:라인 또는 명령}
재시도 횟수: {N회}
중단 이유: {1줄}
필요 조치: {사용자에게 요청할 내용}
```

## §4 절대 금지 사항 (MANDATORY)

| 금지 행위 | 이유 |
|----------|------|
| 에러 무시하고 진행 | 잘못된 상태로 후속 작업 오염 |
| 침묵 재시도 (사용자 알림 없이 N회 반복) | 사용자 통제권 박탈 |
| 가정 기반 진행 ("아마 이 파일이겠지") | 데이터 손실·잘못된 수정 위험 |
| 에러 내용 축약 보고 (핵심 생략) | 원인 파악 불가 |
| 사용자 합의 없는 재시도 무한 루프 | 리소스 낭비 + 사용자 혼란 |
| `--force` / `--no-verify` 자의적 사용 | git 보호 메커니즘 무력화 |
| **무인 반복(루프)·§5 표 밖의 자체 재시도 결정** | 무한 중첩 발생 위험. 재시도 한도는 아래 §5 표가 유일한 정본이다(코드·테스트 수정 루프 G-E·Ralph 의 횟수는 `loop-auto.md` 가 정본) |

## §5 에러 재시도 한도 표

> **적용 범위**: 에이전트가 작업 수행 중 만나는 도구·명령·환경 에러의 **운영 재시도 한도** (분류별 상이). 아래 "§ Retry 정책"(작성 코드 내부의 retry 구현 표준, cap ≤3)과는 별개 축 — 혼용 금지. 코드·테스트 수정 루프(G-E 3회·Ralph N회)도 별개 축이며 한도 정본은 `loop-auto.md` 이다.

| 분류 | 즉시 재시도 | 최대 재시도 | 에스컬레이션 |
|------|-----------|-----------|------------|
| TOOL_BLOCKED | 승인 후 1회 | 1회 | 사용자 거부 시 |
| MCP_UNAVAIL | 2회 | 2회 | fallback 전환 |
| CMD_FAIL | 1회 (멱등 명령만) | 5회 | 5회 실패 시 |
| FS_ERROR | 0회 (경로 확인 후) | 3회 | 3회 실패 시 |
| CONSENT_NEEDED | 0회 (중단) | 0회 | 즉시 |

## § Retry 정책 (MANDATORY — LLM 제어 retry 금지)

> **적용 범위**: 생성·수정하는 **코드 내부**의 API/네트워크 retry 구현 표준. 위 §5(에이전트 운영 재시도 한도)와 별개 축 — 예: CMD_FAIL 운영 한도 5회는 코드 retry cap ≤3과 충돌하지 않는다.

### 원칙
- **LLM이 스스로 retry 결정 금지** — 무한 중첩 발생 위험
- retry는 코드 제어로만 — exponential backoff + 명시적 cap

### 코드 제어 retry 표준

| 항목 | 기준 |
|------|------|
| 최대 시도 횟수 | ≤ 3 (cap 명시) |
| 초기 backoff | 2초 |
| 증가 factor | 2 (exponential) |
| 최대 backoff | 30초 |
| 조건부 retry | 504/429/timeout 등 명시 status만 |

### 비-retry 조건 (즉시 종료)

- 인증 실패 (401, 403)
- 권한 부족 (file permission)
- 사용자 의도와 무관한 시스템 에러
- 동일 에러 메시지 2회 연속 (Reflexion 패턴)

### LLM 에이전트의 행동
- 실패 감지 → **사용자에게 보고**, 또는 main에 에스컬레이션
- 스스로 같은 subagent를 다시 부르지 않음
- 다른 전략 또는 다른 에이전트로 전환 권고

근거: techaheadcorp Inference Cost Explosion 2025, tianpan.co Agentic Systems 2026 — LLM 제어 retry가 비용 폭증·시스템 장애의 주원인.
