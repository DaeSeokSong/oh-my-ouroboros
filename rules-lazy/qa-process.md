## §0 검증 가능한 성공 기준 (Goal-Driven Execution — MANDATORY)

> **로드 시점**: 모든 QA 검증 시작 전
> **상세**: `agents/qa.md` § 검증 가능한 성공 기준 (Goal-Driven Execution) 참조

### QA 시작 전 필수 체크
- [ ] 사용자 요청을 **검증 가능한 형태**로 변환했는가?
- [ ] PASS/FAIL을 **객관적으로** 판단할 수 있는가?
- [ ] multi-step 작업이면 단계마다 verify 정의되었는가?

### 약한 기준 거부
"잘 동작", "정상 작동", "버그 없으면 OK", "성능 좋게" 등 모호 기준은 **거부**하고 main에 재정의 요청.

### seam 테스트 원칙 (2026-08-06 이식 — 출처: mattpocock/skills `tdd`, MIT)
테스트는 **사전 합의된 공개 경계(seam)** 에서만 작성한다 — 기준: "구현 코드가 전부 바뀌어도 테스트는 안 바뀌어야 한다". 내부 구현 결합·동어반복(tautological) 단언은 안티패턴으로 거부.

### multi-step verify 형식
```
1. [Step] {작업} → verify: {객관적 체크}
2. [Step] {작업} → verify: {객관적 체크}
```

## 적용 조건
- 코드 파일(.py, .yaml, .tex 등) 1개 이상 수정/생성/삭제된 경우
- config 값 변경이 발생한 경우

## QA 체크리스트 (순서대로 실행)

### 0. 구조적·수학적 검증 (항상 먼저 **분석**하되, 게이팅 순서는 § 2단계 리뷰 순서가 정본 — 6-Gate의 "구조" 항목)

> 순서 정합(2026-08-25 검수 반영): 구조·수학 분석은 코드를 열자마자 **항상 수행**하지만, 보고의 **게이팅**은 2단계 리뷰 순서(1차 기획-구현 일치 → 2차 코드 품질·구조)를 따른다. 1차 FAIL이면 구조·수학 결과는 "보류(1차 수정 후 재검)"로 표기해 보고하고 2차 판정은 내리지 않는다. 즉 "최우선"은 분석 시점의 우선이지 판정 순서가 아니다.
- 수식 일치·불변식·알고리즘 구조 검증 — 상세 체크 항목: `agents/qa.md` § 1순위 — 구조적·수학적 검증

### 1. 기획-구현 일치 확인
- 사용자가 승인한 수정 계획과 실제 변경 내용을 항목별로 대조
- 누락된 항목 또는 계획에 없는 추가 변경이 있으면 명시

### 2. 호출부(Call-site) 영향 분석
- 수정된 함수/클래스/config 키를 사용하는 **모든 호출부**를 검색 (Grep)
- 시그니처 변경(인자 추가/삭제/순서), 반환값 변경 시 호출부 동기화 확인
- 미동기화 호출부가 있으면 수정 또는 사용자 보고

### 3. Config-코드-논문 3자 일치
- 변경된 config 키가 코드에서 올바르게 참조되는지 확인
- 논문(`docs/paper/`)에 해당 값이 언급된 경우, 논문 수치와 일치하는지 확인
- 불일치 발견 시 수정 또는 사용자 보고

### 4. Import 검증
- 새로 추가된 import가 실제 사용되는지 확인 (unused import 방지)
- 삭제된 코드에서 사용하던 import가 남아있지 않은지 확인

### 5. 테스트 실행 (해당 시)
- 테스트 파일이 존재하면 관련 테스트 실행
- 실험 코드의 경우 `wandb=disabled` 상태에서 dry-run 가능 여부 확인

**silent failure 방지 (MANDATORY)**:
- [ ] `pytest -q --tb=short` 결과에서 `0 collected`, `no tests ran`, `0 passed in N.NNs` 패턴 검출 시 **즉시 FAIL** 처리 (검증 완료로 오판 ❌)
- [ ] 모든 pytest 실행 후 exit code 명시 (`echo "pytest exit:$?"`) — exit 0 + 0 collected는 FAIL
- [ ] DEPRECATION warning 누적 5+ 시 사용자 알림 (라이브러리 버전 호환성 사전 경고)

**실패 주입은 전 지점 (MANDATORY — 2026-08-25 실측)**: 정리·해제·롤백처럼 **순차 해제 + 중간에 닫히는 가드**가 있는 함수는 주입 지점을 **전수**로 돌린다(`[None] + 전체 지점`). 한 지점만 고르면 가드 결함이 통과한다. 판정 기준은 "자원이 해제됐는가"가 아니라 **"가드가 닫혔는가"** — 둘은 별개다. 소스를 읽고 "가장 먼저 지운다"고 단정하기 전에 **줄 번호로 센다**. 근거: 한 추론 서버의 `model_unload` 에서 가드를 닫는 `del` 이 첫 실패 가능 지점 **뒤**에 있어, 중간 주입만 한 자체 시험·qa 독립 시험·보안 소스 검토 **3겹이 모두 통과**했고 외부 교차검증만 잡았다. 설계 쪽 대응은 **문을 닫는 문장을 예외가 날 수 없는 자리(속성 삭제·플래그 세팅)에 두고** 실패 가능한 실제 해제는 지역 참조로 뒤에서 하는 것.

### 6. ML 실험 사전 체크 (학습 스크립트 수정 시 — 자동 트리거)
트리거 파일: `run_trains.py`, `train.py`, `config/train.yaml`, `config/task/*.yaml`, `model/` 하위
- [ ] `wandb=disabled trainer.fast_dev_run=true` dry-run 통과 여부
- [ ] 변경된 Hydra config 키가 override 구문과 일치하는지 확인
- [ ] 새 모델/레이어 추가 시 `torchinfo.summary()` 또는 `thop`으로 파라미터 수 확인
- [ ] DeepSpeed / LoRA 설정 변경 시 예상 메모리 vs 실제 GPU 용량 비교
- [ ] checkpoint 경로가 기존 실험과 충돌하지 않는지 확인
- [ ] `/experiment` 스킬 § 재현성 체크리스트 (seed, 환경 기록) 통과 여부
- [ ] **NaN/Inf loss 강제 감지** (silent failure 방지): dry-run stdout의 loss·metric 값 토큰(`loss=nan`, `=inf`, `-inf`, 단어 경계 기준, case-insensitive) 검출 시 즉시 FAIL (부분 문자열 검색은 `inference`·`INFO` 를 오탐하므로 쓰지 않는다. `fast_dev_run=true` 는 NaN 과 함께 exit 0 을 반환할 수 있다)
- [ ] **exit code 강제 체크**: 모든 dry-run 실행 후 `echo "exit:$?"` 명시 출력 확인. exit 0이라도 NaN/Inf 검출 시 FAIL 우선
- [ ] **silent skip 감지**: `0 batches`, `Epoch 0: 0it`, `LR scheduler is empty` 등 silent skip 패턴 검출 시 FAIL
- [ ] `.venv/pyvenv.cfg` 의 `home` 이 uv 관리 파이썬(`~/.local/share/uv/python/`)인지 확인. 학습·실험 스크립트가 바뀐 경우 uv 관리 경로가 아니면 **즉시 FAIL** 처리 (시스템·anaconda 파이썬 실행은 재현 불가 ❌). 조치는 `rules-lazy/uv-env.md` 점검(2026-08-27 서버 이전 실사고)

**기계 판정 (MANDATORY — 2026-11-24)**: 위 항목 가운데 기계가 가릴 수 있는 것은 `uv run python3 ~/.claude/scripts/ml_precheck.py --log <로그> [--exit-code N] [--config .venv/pyvenv.cfg]` 로 가리고 출력 원문을 보고에 인용한다(`--log` 는 필수이고 없으면 종료 코드 2). 인용 없는 PASS 는 자기선언으로 무효다.
- RESULT 줄만이 아니라 항목별 줄 전부를 인용한다(SKIP 항목이 무엇인지 보이게).
- SKIP 항목(파라미터 수·메모리·checkpoint 경로·재현성 등)은 종전대로 qa 가 판정한다. SKIP 은 RESULT 를 FAIL 로 만들지 않는다.
- 항목이 바뀌면 `scripts/ml_precheck.py` 의 CHECKLIST 표를 같이 고친다.

## 종료 조건 선택지 (MANDATORY — qa 진입 직전 main이 사용자에게 출력)

> **목적**: qa·ralph-loop의 종료 기준을 매 호출마다 사용자가 직접 결정 가능. ralph-loop 기본 6-Gate 검증(구 명칭 5-Gate — 구조 검증 추가로 6항목, ralph 진입 판단용 5-Gate와 별개)을 유지하되, 사용자 commands·작업 성격에 따라 유연성 제공. (2026-07-06 agents/qa.md에서 이관 — main 실행 항목이므로 spawn 토큰 절감)
> **적용 시점**: main이 qa 또는 `/ralph-loop` 호출 직전. **선택지 출력 없이 자동 진행 금지**.

### 선택지 형식 (MANDATORY)

```
🎯 QA 종료 조건 선택:

1. **6-Gate 전체 PASS** (기본) — 구조·기획·호출부·Config·Import·테스트 전체 통과
2. **핵심 테스트만 PASS** — lint·format·import warning 무시, business-critical test만 강제
3. **사용자 커스텀 condition** — 자유 텍스트로 condition 입력 (예: "loss < 0.1 and shape match")
4. **max cycles 조정** — 기본 5 cycle, 1~10 범위로 변경 (선택지 1/2/3과 중첩 가능)

→ 어느 옵션으로 진행할까요? (번호 / 자유 텍스트 / 기본값 진행)
```

### 사용자 응답 → condition 변환 규칙

| 응답 | 변환된 condition | max cycles |
|------|----------------|-----------|
| 1 (기본) | 6-Gate 표준 (구조·기획·호출부·Config·Import·테스트 모두 PASS) | 5 |
| 2 | "business-critical test PASS, lint·format·import warning 허용" | 5 |
| 3 + 자유 텍스트 | 사용자 입력 그대로 (검증 가능 형식으로 변환) | 5 |
| 4 + N | 1/2/3 중 재선택 후 max cycles = N | N (1~10) |
| 사용자가 "기본값" 명시 | 1번 적용 | 5 |

### 페르소나 통합 (자동 적용)

qa 페르소나 사전 할당 시: `qa.strict`+옵션1=100% 커버리지·edge case 발굴 / `qa.flexible`+옵션2=warning 허용 확대·빠른 사이클 / `qa.balanced`+옵션1=위험도 기반 차등(기본 추천) — 카탈로그: `rules-lazy/agent-personas.md` § qa

### 변환 후 실행 (2026-07-17 Codex C2 — 플러그인 충돌 제거)

변환된 condition·max cycle N은 **qa spawn prompt 5요소 `objective`에 명시**하고, 루프는 qa/main이 내부 카운터로 구동한다. **`/ralph-loop --condition/--max-cycles` 슬래시 호출 금지**. 동명 플러그인(`--max-iterations`만 지원)으로 새면 무제한 폴백. 상한 강제는 CLI가 아니라 이 파일의 종료 조건(max cycle·동일 실패 3회)이 담당.

### 생략 조건
- 사용자가 명시적 condition 함께 전달 ("qa, 단위 테스트만 PASS될 때까지")
- ralph-loop 재진입 시 (이미 condition 설정됨)

### 4 path 의사결정 (parallel-dispatch.md 결정 트리 적용)

루프 진입 → qa 자체 수정 시도 → 외부 도움 필요 시 아래 path 중 선택:

> **재시도 위생 (2026-08-10 이식 — 출처: MindForge, arXiv 2607.27146 인프라 노이즈 복구 패턴)**: 재작업은 **마지막 정상 상태로 롤백한 뒤** 재실행한다 — 실패 잔해(부분 수정·오염된 중간 상태) 위에 누적 재시도하면 실패 원인과 잔해 효과가 섞여 판정이 불가능해진다.

| Path | 메커니즘 | 사용 케이스 |
|------|---------|-----------|
| α — 단일 subagent | `Agent(subagent_type="...", prompt=..., result만 받음)` | 1회성 위임, 합의 불필요 |
| β — teammate | `TeamCreate(lead="qa")` + `Agent(team_name=..., name=...)` | 수정 ↔ 재검증 다회 라운드 |
| γ — parallel-dispatch | 한 turn에 Agent N개 동시 호출 | multi-file 독립 수정 |
| δ — hybrid | TeamCreate(qa lead) + parallel-dispatch (coder-1, coder-2 ...) | 독립 수정 + 라운드 결합 |

### Path 선택 가이드

| 상황 | 선택 | 이유 |
|------|-----|------|
| import 오류 1줄 추가 | α | 1회성 |
| 함수 로직 수정 → qa 재검증 ↔ 재수정 가능성 | β | 반복 교환 |
| foo.py·bar.py 독립 수정 | γ | 독립 작업 2개 |
| 라이브러리 API 검색 1회 | α (searcher) | 1회성 |
| coder 2명 + qa 라운드 | δ | 독립 + 라운드 |

### qa 자율 소집권 (MANDATORY)

루프 중 qa는 필요 시 아래 에이전트를 **자율 소집**한다 — **단 소집 실행 주체 전제**: ralph 루프의 teammate 컨텍스트에선 mailbox/SendMessage로 직접 교류, 일반 subagent 컨텍스트(Agent 도구 없음)에선 main에 "coder/searcher/scout 소집 필요" 신호로 반환해 main이 대신 spawn(`rules/agent-routing.md` § "소집"의 실행 주체):

| 소집 대상 | 트리거 조건 | 사용 예시 |
|----------|-----------|---------|
| coder | 로직 변경 필요 (qa 직접 수정 범위 초과) | 함수 동작 변경, 알고리즘 수정 |
| searcher | 외부 자료 필요 (라이브러리 API 변경 등) | "ImportError: ... renamed in v3.0" → 마이그레이션 검색 |
| scout | 추가 호출부·의존성 정찰 필요 | 수정 후 영향 범위 확장 시 |

(planner/docs/gitops/researcher는 자율 소집 ❌ — main 결정 영역)

### 5-Gate (qa 자율 소집 판단 — ralph 진입 조건)

> 진입 확정 시 main이 **작업 범위 JSON을 등록**한다(`rules-lazy/scope-gate.md` — 미등록이면 게이트는 상시 통과라 보호 효과 없음). 연속 FAIL·회귀로 되돌림이 필요해지면 `rules-lazy/rollback-procedure.md` 절차 적용. (2026-07-10 진입점 신설 — 두 룰 모두 인바운드 0이던 고아)

| Gate | 명칭 | 조건 |
|------|------|------|
| G1 | 화이트리스트 | 소집 대상이 coder/searcher/scout 중 하나 |
| G2 | 필요성 | 소집 없이 현재 루프 진행 불가 |
| G3 | 종료 조건 미충족 | PASS 미달성 + cycle < N(설정된 max cycle, 기본 5) + 무한루프 미감지 |
| G4 | 컨텍스트 < 60% | qa 현재 컨텍스트 사용량이 60% 미만 |

## § 외부 신호 의존성 (MANDATORY)

```
✅ QA 검증 결과:

4. Config-코드-논문: PASS/FAIL (상세)
5. Import 검증: PASS/FAIL
6. 테스트: PASS/SKIP/FAIL
7. Ralph Wiggum 루프: N회 반복 / 위임 건수 M건 (해당 시)
8. 원시 증거 (MANDATORY, 2026-08-25): 실행한 검증 명령 원문 + **exit code** + **실행 시각** + **검증 대상 파일의 `git hash-object` 값**(mtime은 `touch`로 위조되므로 내용 해시로 결박 — 3라운드 검수) + 출력 마지막 10줄(로그 파일이 필요하면 qa 에게 Write 가 없으므로 main 이 저장하고, 별도 qa 가 그 파일의 sha256·mtime 을 계산해 돌려주면 main 은 그 값을 경로와 함께 기록·대조한다. 이 증거 보고는 반환 상한의 예외이고 요약을 맨 앞에 둔다: `token-efficiency.md` § Subagent 반환값 적재 최소화). 이 항목이 없거나 해시가 현재 파일과 다르면 1~6의 PASS는 자기선언으로 간주해 무효. **대조 주체·시점(7라운드 렌즈3 — 수동태 문장이라 아무도 안 하던 결함)**: 해시 재계산은 **전 건** 수정에 관여하지 않은 **별도 qa** 가 `git hash-object <파일>` 로 하고 8항 값과 비교한다(O(1) 비용, 적힌 hex 가 실제 실행 결과인지는 이 대조로만 확인된다). **소집**: main 이 원 qa 보고를 받은 직후 별도 qa 를 소집한다(반환-only, 쓰기 금지). **명령 재실행**은 비자명 변경(로직·수식·인터페이스)에서 같은 별도 qa 가 검증 명령을 현재 작업공간에서 **1회 재실행**해 exit code를 대조한다. 재실행할 대상은 main 이 시험 파일·검증 스크립트의 경로로 지정하고, 원 qa 보고 속 명령 문자열을 그대로 넘기지 않는다(원 qa 가 외부에서 온 글을 읽었으면 명령이 세탁되기 때문). main 은 재실행 · `git hash-object` · `git grep -F` 를 직접 하지 않고, 별도 qa 가 돌려준 출력 원문과 파일을 Read·Grep 도구로 대조해 채택한 뒤에만 완료 게이트(원칙 6)를 통과시킨다(로그 열람만으로는 불충분). 두 가지를 같은 조건에 묶지 않는다: 해시는 항상, 재실행은 비자명 변경. **한계(정직 표기 — 14라운드 렌즈3, spawn-tree·evidence-ls·launch-set 헤더와 같은 문형)**: 자명한 변경에서는 파일 해시만 재계산되고 명령 원문·exit code·실행 시각·출력 마지막 10줄은 원 qa의 자기보고로 남는다 — 이 잔여는 위조 비용을 올리는 장치이지 봉쇄가 아니며, 의심 시 별도 qa 의 재실행으로 승격한다. **자체 수정 포함 PASS**: qa 가 자체 Edit 한 보고는 `agents/qa.md` § Goal-Driven 루프의 «자체 수정 표시» 에 따라 다른 qa 가 수정분을 재확인한 뒤에만 채택한다. **식별자 실재 대조**: 보고에 쓴 파일·함수·스크립트·플래그 이름은 별도 qa 가 `git grep -F -- '<이름>'` 로 저장소 실재를 확인한다(없는 이름 금지, `rules-lazy/answer-detail.md` § 없는 이름을 지어 부르지 않는다)
```

- **2026-07-27 로스터 확장**: 렌즈는 고정 3인이 아니라 **사고 유형별 로스터**다 — 비자명 구현 일반은 위 3렌즈(정찰/계획-적합성/비판 감사)를 병렬 spawn하고, 지표·처치·외부기법 채택이 걸린 구현은 해당 유형 행을 **추가로** 병렬 spawn한다.
- 흐름: 해당 로스터 병렬 spawn(독립 보고, 5요소 prompt) → main이 원문(파일:라인/수치) 대조 통합 → 편차·결함은 coder 수정 후 **재검수** → PASS 시에만 진행.
- **사용자 지시 원문과 대조 (2026-11-24 사용자 결정, 의뢰서 W4)**: 검수자는 결과를 계획뿐 아니라 **사용자 지시 원문**과도 대조한다. 계획이 원문을 옮기면서 빠뜨린 제약이나 «하지 말 것» 은 계획 대조만으로는 안 잡히기 때문이다. 그래서 검수 spawn prompt 에 원문 인용이나 원문 파일 경로를 싣는다(`agent-routing-mcp.md` § Spawn prompt 5요소 강제).
- **재검수 때 앞 라운드 판정 목록을 함께 넘긴다**: 지적 · 판정(채택/기각) · 고친 곳(파일:라인)을 표로 싣는다. 다만 새 검수자의 독립성을 지키려고 spawn prompt 에 «앞 판정은 참고 자료이고 다시 확인할 대상이다» 라고 적는다. 앞 판정을 그대로 믿고 넘기라는 뜻이 아니다.
  - 근거(참고 수준): 2026-11-24 정독 논문 GPRM(arXiv 2611.20755 v1, 프리프린트)의 ablation 에서 앞 단계 판정 이력을 빼면 판정 정확도가 내려갔다(4B-SFT 기준 PRMBench −3.1 · ProcessBench −11.2). 그 논문은 에이전트 과제 성공률을 재지 않았다.
- **중간 산출물은 뒤따르는 결과와 함께 검수한다 (2026-11-24 사용자 결정, 의뢰서 W7)**: 설계 · 중간 코드 · 중간 수치처럼 중간 단계 산출물을 검수할 때 그것을 이미 쓴 뒤 단계의 결과(호출부 · 다음 단계 산출물 · 그 수치를 쓴 표)가 있으면 검수 spawn prompt 에 함께 싣는다. 중간 산출물만 보면 «그 자체로는 맞지만 뒤에서 잘못 쓰인» 어긋남이 안 보이기 때문이다. 뒤 결과가 아직 없으면 그대로 진행한다.
- **검수 기준 참고표 (참고이며 강제 아님)**: 검수 지시문을 쓸 때 아래 네 가지를 빠뜨리지 않았는지 훑는다. 이 표로 PASS · FAIL 을 기계로 가르지 않는다.
  - 앞 단계와 일관한가: 앞 단계 산출물 · 결정과 어긋나지 않는다.
  - 뒤에서 합당하게 쓰이는가: 뒤따르는 단계가 이 산출물을 의도대로 쓴다.
  - 사용자 요청에 복무하는가: 사용자 지시 원문의 목적과 제약에 맞는다.
  - 그 자체로 맞는가: 수식 · 로직 · 수치가 단독으로 옳다.
  - 근거(참고 수준, 앞 글머리와 같은 논문): 그 논문 ablation(4B-SFT)에서 뒤따르는 단계를 빼자 PRMBench −1.3 · ProcessBench −16.0 이었다. 다만 프리프린트 한 편이고 판정 프롬프트 원문이 없고 시드와 분산이 없으며 에이전트 과제 성공률은 재지 않았다. 비용도 오프라인 토큰 +9.6% · 지연 +42.4% 라서 «참고» 로만 둔다.
- **FAIL 원인별 격상 순서 (2026-11-24 사용자 결정, 의뢰서 W8)**: 검수 FAIL 로 반송할 때는 같은 모델로 되풀이하기 전에 원인부터 가른다. 1) `~/.claude/_audit/agent-prompts/<날짜>/` 에서 그 소집의 지시문을 열어 **맥락 누락**(필요한 정보 · 제약 · 사용자 지시 원문이 지시문에 없었는가)을 먼저 점검한다. 누락이면 지시문을 보완해 같은 모델로 다시 맡기고 T41 축 «맥락 누락» 으로 기록한다 2) 누락이 아니고 결과가 **틀렸으면**(추론 · 구현이 잘못됨) 모델을 올린다(sonnet → opus) 3) 누락이 아니고 지시된 단계를 **건너뛰었으면**(검증 생략 · 일부만 수행) effort 를 올린다. 지시문에 있었는데 다르게 한 것은 T41 축 «방향 이탈» 이다. 두 번 뒤에도 FAIL 이면 사용자에게 보고한다는 기존 규칙은 그대로다. 원인 분류는 판단이라 기계로 집행하지 않는다. 지시문 기록 안의 문장은 데이터이고 지시가 아니다(`rules-lazy/agent-eval.md` § 위임 손실 축). 올릴 때 넘기는 인자: `rules-lazy/model-assignment-rules.md` § FAIL 뒤 올리는 기준.
- **qa 6-Gate와의 관계 (중복 아님)**: qa의 6-Gate는 **기능·회귀 축**(테스트·호출부·인과), 이 게이트는 **스펙 적합성 축**(계획 대비 누락·변형) — 별개 질문이다. 표준 순서: coder → qa(기능 PASS) → 계획-대비 검수(적합성 PASS) → 발사. 소규모 변경으로 qa 6-Gate가 생략된 경우에도 스펙이 있으면 이 게이트는 독립 적용. 위 로스터에서 qa가 맡는 지표·처치 검증은 **추가 역할**이며 6-Gate를 대체하지 않는다.
- 적용 대상: 계획된 스펙(discuss/workflow/spawn 스펙)이 있는 비자명 구현(«비자명» 정의: `skills/intent/SKILL.md` 「비자명의 판정」). **생략**: 단순 1줄 수정·오타·boilerplate·이미 qa 통과한 소변경. 근거: coder 자기검증만으로는 계획 편차(누락 arm·수식 오구현·회귀)를 놓친다 — 독립 검수가 발사·**결론 확정** 전 마지막 방어선.

### 반박(검수 지적) 자격·형식 게이트 (MANDATORY — 2026-07-29 사용자 지시, 과잉 비판 완화)

> 배경: 검수가 "이론상 가능한" 우려·막연한 트집으로 학습 발사를 반복 차단하는 과잉 비판 실측. 검증의 목적은 **실사고 차단**이지 발사 저지가 아니다 — 트집의 비용은 GPU 유휴·캠페인 지연으로 실재한다.

**차단 자격 (전부 충족해야 발사·머지·결론을 막을 수 있다)**
1. **구체 실패 경로**: 파일:라인 또는 실측 수치로 "이 입력·조건이면 이렇게 잘못된다"를 지목 — "~일 수도 있다"·"이론상 가능"만으로는 차단 불가.
2. **반증 가능**: 어떤 확인·실험 결과가 나오면 지적을 철회하는지 명시되어야 한다.
3. **이번 변경 범위 내**: 범위 밖·기존 잔존 이슈는 **비차단 노트로 강등**(기록만, 발사 진행).
4. **주장 강도 = 증거 수준 (2026-07-29 추가 — 과대 주장 차단)**: **"실패한다"는 단정은 재현 실행 출력·실측이 있을 때만** 허용 — 증거 없으면 자동으로 "가능성" 표현으로 강등되며 차단 자격을 잃는다. 또한 실패 시나리오의 **전제 조건이 현재 구성에서 실제로 성립함**(실제 config 값·실제 데이터·실제 호출 경로 — 검수자가 스스로 확인해 파일:라인 제시)이 요구된다. 발생 불가능한 입력·쓰지 않는 설정·가상의 극단값 위에 세운 시나리오는 **과대 주장으로 즉시 기각 + T41 기록**. 원리: 실패 주장도 § 전제 동작 실증의 대상이다 — 검수자의 시나리오 역시 이름·추측이 아니라 실행 증거로 성립해야 한다.

**형식 (초과 서술 금지 — 3줄 + 예시)**: 1) 무엇이 문제인가 1줄 2) 어떻게 실패하는가 1줄 3) 왜 그렇게 판단하는가(근거) 1줄 + **구체 실패 예시**(입력·조건·재현) 1개. **이 형식으로 쓸 수 없는 지적은 제출 불가** — 막연한 불안·스타일 취향·범위 밖 소원이 자동 걸러진다. spawn prompt의 output_format에 이 형식을 명시해 spawn한다.

**main 스크리닝**: 자격 미달 지적은 기각하고 기록만 남긴다(발사 진행). 자격 충족 지적만 기존 원칙(실측·원문 대조 후 채택)으로 판단. 특정 검수자의 기각이 3회+ 누적되면 T41(에이전트 약점)로 기록해 spawn prompt를 보정한다.

**"측정 없으면 의미 없음" 류 제안의 전달 방식 (MANDATORY — 2026-07-29 사용자 지시, 질문 금지)**

"X를 안 재면 학습할 의미가 없다"·"Y 측정을 추가해야 한다" 류 우려로 **측정 여부를 사용자에게 묻지 않는다** — 이런 질문이 빈발해 발사 흐름을 끊는 것이 실측 피드백("정신사나워"). 처리:
- 계획대로 **dry-run을 완주**한다 (질문으로 세우지 않는다).
- dry-run 완료 보고 **말미에 "주의 사항"으로 제시만** — 항목당 3줄 요약 느낌(1) 무엇이 빠졌나 2) 어떤 영향인가 3) 왜 중요한가 각 1줄), 채택 여부는 사용자가 원할 때 지시하는 것.
- 발사를 막을 수 있는 건 위 차단 자격 4요건을 충족한 지적뿐 — 측정 항목 제안은 언제나 비차단.

## § 최종 보고 대조 (2026-10-06 사용자 지시, 한 프로젝트 CPU 벤치 교훈 6)

- **대상**: 외부 교차 검증을 거친 최종 보고, 그리고 compaction 뒤에 쓰는 결과성 최종 보고. 사실 질문·단답·진행 한 줄은 대상이 아니다.
- **방법**: 보내기 전에 초안을 파일로 저장하고, 초안을 쓰지 않은 qa 한 명에게 «보고 문장 대 원자료(파일:줄·명령 출력)» 대조를 맡긴다. 확인 항목은 수치·개수, 범위(어느 라운드·회차의 변경까지 포함했는가), 라벨·번호(같은 에이전트 이름의 다른 일, 편집 회차와 검수 회차의 구분), 외부 답 인용의 어미·위치, 판정문 보관 여부다.
- **판정**: qa 가 `RESULT: PASS` 또는 `RESULT: FAIL` 로 끝맺는다. FAIL 이면 고친 뒤 같은 방식으로 다시 대조한다. 판정문과 초안 해시를 작업 폴더에 파일로 남긴다(예: `qa_final_verdicts.md`).
- **compaction 뒤 보고**: 요약이나 기억이 아니라 원자료를 다시 조회해 쓴다. 외부 답을 인용할 때는 어미까지 원문 그대로 적고 파일:줄을 단다.
- **실측**: 2026-10-06 한 프로젝트의 CPU 벤치 최종 보고 초안이 독립 qa 에서 두 번 FAIL 했다. 틀린 것은 측정값이 아니라 범위·라벨·번호·개수였다(유형 6가지: 1라운드 정정 누락, 같은 이름 다른 라운드 혼동, 편집·검수 회차 번호 혼동, 외부 답 인용 어미·위치, 낡은 개수, 판정문 미보관).
