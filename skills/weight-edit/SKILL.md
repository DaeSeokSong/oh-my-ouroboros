# /weight-edit: 가중치 편집을 절차 · 기록 · 누적 비교로 굳히는 스킬

> 의뢰서: `intent/2026-11-11-weight-edit-skill.md` · 계획: `docs/superpowers/plans/2026-11-11-weight-edit-skill.md` · 기법 근거: `knowledge/harness/weight-edit-methods-verified-2026-11-11.md`(인용 검증본).
> 이 스킬은 **절차와 기록을 보장하고 성능 향상은 보장하지 않는다.** 문헌으로도 checkpoint 하나만으로 재학습 없이 정확도를 올리는 기성 기법은 확인되지 않았다. 발단이 된 글(블로그, 심사 없음)은 «탐색적 관찰» 로만 인용하며 대조군이 없다. 그 빈자리(대조군 · 사전 판정 규칙 · 누적 기록)를 이 스킬의 절차가 채운다.

## 1. 언제 쓰나 · 범위

- 대상: 학습이 끝난 checkpoint 에 **재학습 없이** 가하는 편집(경량화 · 출력 보정 · 표적 편집 · 방향 제거 · 병합). 편집 뒤 미세 조정이 따르는 기법은 §6 표에서 «범위 밖» 이고 절차에 넣지 않는다.
- 편집 한 건 = 누적 파일(ledger)의 JSON 한 줄이다. 한 건이 끝나면 `check_ledger.py` 로 검사하고 `compare_ledger.py` 로 이전 건과 비교한다.
- **실행은 사용자**다. 에이전트는 스크립트 · 명령서(.sh) · 보고 · 누적 표를 만들고, 읽기 전용 스크립트(가중치 요약 · 기록 검사 · 비교 표)만 직접 실행한다.
- **원본은 읽기 전용**이다. 편집은 항상 사본에 하고 사본은 프로젝트의 로컬 checkpoint 자리에 둔다(네트워크 파일시스템 금지).
- **원시 가중치 값을 문맥에 넣지 않는다.** 요약 스크립트의 출력으로만 읽는다(§7).
- 하네스가 싣는 도구는 기록을 다루는 두 스크립트뿐이다. 가중치를 읽거나 고치는 스크립트는 사례마다 프로젝트 세션이 §7 명세대로 만든다.
- 프로젝트 고유 값(누적 파일 위치 · 기준 모델 · 판정 기본값 · 다른 능력 지표 이름)은 프로젝트 등록부 `weight_edit.*` 에서 읽는다(`config/projects/README.md`). 이 문서에는 프로젝트 · 판 · 서버 이름을 쓰지 않는다.

## 2. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| main | 결정 · 통합 · 단계 통과 판정 · 결과 보고 | 원시 가중치 읽기 · 편집 스크립트 실행 |
| planner 또는 researcher | 가설 · 사전 판정 규칙 초안 · 기법 선택 자문 | 최종 결정 |
| coder (프로젝트 세션) | 요약 · 편집 · 평가 스크립트와 실행 명령서(.sh) 작성 | 실행 |
| qa | 기록 한 줄과 근거 파일(evidence)의 대조 · 검사 스크립트 실행 | 기록 수정 |
| 사용자 | 편집 스크립트와 평가 실행 · 결정 · 외부 모델 승인 | |

## 3. 한 건의 순서 (11단계)

| 단계 | 하는 일 | 통과 조건 |
|---|---|---|
| 1 | 대상 고르기와 원본 해시 | 원본 경로 · sha256 기록. 같은 원본의 baseline 줄이 있거나 이번에 만든다 |
| 2 | 가중치 요약 읽기 | 요약 스크립트 출력만 읽음(층별 모양 · 통계 · 희소도 · 특이값 요약). 원시 값 덤프 없음 |
| 3 | 실패가 국소적인지 진단 | 고칠 실패가 어느 층 · 클래스 · 입력에 모이는지 근거와 함께 적음. 국소적이지 않으면 «탐색» 으로만 진행 |
| 4 | 가설과 사전 판정 규칙 | 편집 **전에** 판정 규칙 글을 적고 시각을 남김(`written_before_edit`) |
| 5 | 편집 계획 | 사본 경로 · 평가 횟수 예산 · 편집 선택용 자료와 성능 보고용 자료의 분리 · 대조군 종류 · 반복 방법 |
| 6 | 스크립트와 명령서(.sh) | 편집 스크립트가 §7 규칙을 지킴. 명령이 2개 이상이면 .sh 로 묶어 줌 |
| 7 | 사용자 실행 | 사용자가 직접 실행. 에이전트는 실행하지 않음 |
| 8 | 측정 | 목표 지표 · 다른 능력(망각 확인) · 크기와 속도(파라미터 수 · 저장된 파일 크기 · FLOPs · 지연과 잰 조건), 반복(n ≥ 2), 대조군 |
| 9 | 결과 보고 | 통일된 결과 보고 양식(`rules-lazy/answer-detail.md` § 결과·분석 보고 필수 구조). 결론은 사전 판정 규칙으로만 계산 |
| 10 | 누적 기록 한 줄과 검사 | `check_ledger.py` 종료 코드 0 |
| 11 | 비교 표 | `compare_ledger.py` 출력을 보고에 붙임 |

## 4. 기록 칸 · 검사 · 비교

누적 파일은 JSON 줄 파일이고 한 줄이 한 건이다. 칸의 정의와 시험된 형식은 `tools/weight-edit/README.md` 와 `tools/weight-edit/weight_edit_common.py` 에 있다.

| 칸 | 뜻 |
|---|---|
| `id` · `date` · `project` | 유일한 이름(영숫자로 시작하고 영숫자 · `.` · `_` · `-` 만 가능) · YYYY-MM-DD · 프로젝트 |
| `target` | 원본 `{name, path, sha256_before, sha256_after}`(두 해시는 같아야 함) |
| `copy` | 편집 사본 `{path, sha256}`(baseline 이 아니면 원본 해시와 달라야 함) |
| `kind` · `method_ref` | baseline, prune, quantize, lowrank, merge, output-adjust, rule-edit, direction-removal, other · §6 번호나 출처 |
| `purpose` · `hypothesis` | accuracy, compression, both, explore · 가설 |
| `locality_diagnosis` | 국소성 진단(rule-edit · direction-removal · other 이면 필수) |
| `verdict_rule` | `{written_before_edit, text}` 사전 판정 규칙 |
| `eval_budget` · `changed` | `{planned, used}` · `{params_changed, params_total}` |
| `selection_data` · `report_data` | 편집을 고른 자료 · 성능을 보고하는 자료(서로 달라야 함) |
| `repeats` | `{n, varied}` n ≥ 2 와 무엇을 바꿔 반복했는지 |
| `metrics` | `target`(1개 이상) · `other`(1개 이상) · `size`(params · size_bytes · flops · latency_ms 전후와 `latency_condition`. size_bytes 는 저장된 가중치 파일의 크기이고 양자화는 파라미터 수가 아니라 이 값이 줄어든다. 숫자는 0 이상) |
| `controls` | 대조군 `[{kind, metrics}]` |
| `verdict` · `evidence` | improved, maintained-compressed, no-effect, worse, explore · 근거 파일 경로 |
| `executor` · `agent` · `external_approval` | user 만 · harness 또는 external:<모델 이름> · 외부면 승인 기록 필수 |

```
python3 -I ~/.claude/tools/weight-edit/check_ledger.py <누적 파일>      # 0 통과 · 1 거부 있음 · 2 파일 없음 또는 빈 파일
python3 -I ~/.claude/tools/weight-edit/compare_ledger.py [누적 파일] [--target 이름] [--metric 지표] [--sort 열] [--reference 파일.json]
```

- 비교 표는 열 14개(파일 크기 변화 포함)의 GFM 표이고 머리글에 좋은 방향(↑ ↓)이 붙는다. 표 아래에 판정별 건수와 «improved 인데 대조군보다 못한 줄» 경고가 나온다.
- 경로를 주지 않으면 등록부 `weight_edit.ledger_path` 를 읽는다. 기준 모델 행은 `weight_edit.reference_models`(또는 `--reference`)가 있을 때만 맨 위에 붙는다.
- 검사에서 거부된 줄이 있으면 비교 표는 나오지 않는다. 틀린 기록으로 비교하지 않는다.

## 5. 판정 규칙

| verdict | 기록 검사가 요구하는 것 |
|---|---|
| improved | `written_before_edit` 참과 규칙 글 · `controls` 1개 이상이고 그중 하나 이상이 목표 지표와 같은 이름의 지표를 가짐 · purpose 가 accuracy 또는 both |
| maintained-compressed | `written_before_edit` 참과 규칙 글 · `metrics.size` 네 쌍(params · size_bytes · flops · latency_ms) 전후 값 전부와 지연 측정 조건 · 네 쌍 가운데 하나 이상이 줄어듦(늘어난 쌍은 경고) · purpose 가 compression 또는 both |
| no-effect · worse · explore | 공통 요구만(아래) |

공통 요구(baseline 이 아닌 줄): 원본 해시가 전후로 같음 · 사본 해시가 원본과 다름 · `repeats.n ≥ 2` · `metrics.other` 1개 이상 · `selection_data ≠ report_data`(유니코드 정규화 · 보이지 않는 문자 제거 · 공백 정리 · 대소문자 접기 뒤 비교) · `eval_budget.used ≤ planned` · executor 는 user. baseline 줄은 이 요구에서 빠지고 verdict 는 explore 여야 한다. 사전 규칙과 대조군이 없으면 판정 칸은 «explore» 로만 남는다. 위험 단계는 이 판정이므로 검사는 느슨하게 완화하지 않는다.

**스킬은 절차와 기록을 보장하고 성능 향상은 보장하지 않는다.** 검사 통과는 기록이 규칙을 지켰다는 뜻일 뿐 편집이 좋다는 뜻이 아니다.

## 6. 기법 안내표 (인용 검증본 22건)

성능 수치는 싣지 않는다(초록의 대표 수치가 미세 조정 뒤 값인 경우가 있었다). 검증의 확신도는 중간이다. 열 «이 스킬에서» 의 뜻: **사용 가능** = 재학습 없이 쓸 수 있고 근거 영역이 맞음 · **조건부** = 표의 단서가 충족될 때만(필요한 것 열 참조) · **범위 밖** = 재학습이 따라서 이 스킬이 다루지 않음 · **정보용** = 편집이 아니라 진단 근거.
영상 모델에서 바로 시도할 수 있는 것은 2 · 7 · 8(정확도 유지형 경량화) · 13 · 14(checkpoint 가 여럿일 때) · 15(클래스 불균형일 때) · 17(규칙 편집)이다. 정확도 유지형 경량화는 목표가 «유지» 이지 향상이 아니다.

## 7. 프로젝트 세션이 만드는 스크립트의 명세

**가중치 요약 스크립트**(읽기 전용)가 내야 할 것:
- 층별 이름과 모양 · 통계(평균 · 표준편차 · 최소 · 최대) · 희소도(0 비율) · 특이값 요약(상위 몇 개와 에너지 비율)을 **표 한 장**으로 출력한다.
- 원시 값 덤프를 하지 않는다. 한 층의 출력은 요약 통계 몇 줄로 끝난다.
- 입력 파일을 열기만 하고 쓰지 않는다. 시작할 때 원본의 sha256 을 출력한다.

**편집 스크립트**가 지켜야 할 것:
- **사본에만 쓴다.** 원본 경로에는 쓰기를 열지 않는다(열기만 허용).
- 편집 전후의 원본 해시와 사본 해시를 출력한다(원본 두 해시가 같아야 기록이 통과한다).
- 바꾼 가중치 수와 전체 수(`params_changed`, `params_total`)를 출력한다.
- 평가 횟수 예산(`planned`)을 넘기지 않고 사용한 횟수(`used`)를 출력한다. 나아질 때만 변경을 남긴다(전부 기각돼 사본이 원본과 같으면 마지막 시도 후보를 사본으로 보존한다).
- 편집 선택에는 `selection_data` 자료만 쓰고 성능 보고는 `report_data` 자료로만 한다.
- 실행 명령서(.sh)는 로그를 남기고 비가역 단계 전에 확인을 받는다.

## 8. 외부 모델

- 기본은 **하네스 안 에이전트**만 가중치 편집을 맡는다(`agent: harness`).
- 외부 모델(Codex · Grok)에 **방법 질문**을 할 때는(건별 승인 없는 기본 경로이며 아래 예외와 별개다) 익명화한 질문으로만 한다. 프로젝트 이름 · 경로 · 수치 · 해시를 보내지 않고 외부 전송 규칙(`rules-lazy/untrusted-quarantine.md` § 외부 모델 전송 등급)과 실행 컨텍스트 검사를 따른다.
- 외부 모델이 **가중치를 직접 다루는** 선택지는 전송 규칙의 예외 조항(`rules-lazy/untrusted-quarantine.md` §6, 2026-11-11 반영)에 따라 쓸 수 있다. 고를 때마다 아래 순서를 따른다. 1) 보낼 항목 목록을 보여 준다. 2) 그 건을 다루는 사이클에서 사용자 승인을 받는다. 3) 승인 발화를 `external_approval` 칸과 감시 서명(`scripts/oversight-append.sh external-send`)에 남긴다. 4) 전송 전 검사(`scripts/external_send_preflight.py`)와 모델 · effort 게이트를 거친다. 5) 전송은 main 세션만 하고 체크포인트 파일은 보내지 않는다. 여기서 건은 기록 한 줄(id 하나)이고 여러 건을 묶은 승인은 인정하지 않는다. 승인은 사용자가 그 사이클에서 직접 입력한 글이나 직접 고른 선택 답만 인정한다. 보낼 수 있는 것은 그 건의 편집 대상 모델에서 잰 수치와 그 건의 편집 스크립트뿐이며 평가 자료 · 개인 정보 · 체크포인트 파일 · 무관한 회사 코드 · 미공개 핵심 기법 · 자격증명은 계속 금지다. 승인 기록이 없으면 `agent: external:*` 줄은 검사에서 거부된다. 한계: 기록 검사는 `external_approval` 칸이 비어 있지 않은지만 보고 실제 승인 여부는 감시 서명과의 대조로 확인한다.

## 9. 금지

- 원본 가중치 덮어쓰기.
- 시험(보고용) 자료의 수치를 보고 편집을 고르기. 그 수치는 성능 근거가 되지 못한다.
- 판정 규칙을 결과를 본 뒤에 쓰기(`written_before_edit` 를 사실과 다르게 적는 것 포함).
- 실행 주체 바꾸기. 편집 스크립트와 평가는 사용자가 실행하고 에이전트는 실행하지 않는다.
- 원시 가중치 값을 문맥에 넣기 · 재학습이 따르는 기법을 이 절차에 넣기.
- 대조군 없이 improved 로 적기.
